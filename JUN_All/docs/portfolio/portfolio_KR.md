## 0. 한 줄 / 세 줄 소개 (이력서 상단용)

**한 줄**
> Maya·언리얼·MetaHuman을 잇는 리깅/페이셜 파이프라인 툴을 직접 설계·개발하는 Technical Artist. 14주간 40여 종의 사내 툴과 이를 지탱하는 공용 프레임워크를 구축했습니다.

**세 줄**
> - 아티스트의 반복 작업을 **툴로 제거**하는 데 집중합니다. 수백 회의 수동 반복(포즈별 코렉티브 매칭, 본 단위 물리 노드 세팅 등)을 버튼 한 번으로 대체했습니다.
> - **Maya ↔ Unreal 브릿지**를 텍스트 노드 생성 방식으로 자동화했습니다. Maya의 리그 데이터(조인트/컨스트레인트/오브젝트 배열)를 언리얼 Control Rig·KawaiiPhysics 그래프에 **Ctrl+V로 그대로 붙여넣는** 변환기를 만들었습니다. 이 변환기들을 엮어 **Maya의 splineIK 리그를 언리얼로 이식하고 런타임 물리로 구동**시키는 데까지 실사용했습니다(2-4).
> - 툴을 낱개가 아니라 **파이프라인으로** 만듭니다. 공용 위젯·테마·경로관리·언두·드래그&드롭 설치·릴리스 빌더를 프레임워크로 묶어, 신규 툴을 반나절 단위로 찍어낼 수 있는 구조를 갖췄습니다.
> - 리그의 거동을 **튜닝 가능한 수학 함수로 오소링**합니다. 조인트 체인의 트위스트·디폼을 선형·시그모이드 함수로 설계해(splineIK up-vector 한계 극복, 매트릭스 컨스트레인트 대비 아트 디렉션·실시간 튜닝 우위) **촉수·뱀** 리그를 만들고, **언리얼로 임포트하면 의도한 대로 애니메이션**되도록 했습니다.

## 1. MetaHuman 리그 — 페이셜 · 바디 RBF · 코렉티브 (실사·MetaHuman 파이프라인)

### 1-1. PoseWrangler(언리얼 Pose Driver) 기반 아바타 관절별 의상 주름 코렉티브 자동 생성
`A00280_correctiveFromCache`

- **문제**: 어깨·팔꿈치·무릎 등 관절별로 의상 주름 코렉티브 셰이프를 만들 때, 각 RBF 포즈마다 Houdini 클로스 시뮬 캐시를 보고 Shape Editor로 손으로 형상을 맞추는 작업을 **(포즈 수 × 관절 수)** 만큼 반복해야 했습니다.
- **한 일**: Houdini에서 뽑은 **Alembic 클로스 캐시**를 읽어, 각 RBF 포즈 프레임의 캐시 형상을 스냅샷 → 리그를 해당 포즈로 이동 → PoseWrangler의 `invertShape` 경로로 **바인드(스킨 이전) 델타**를 산출해 코렉티브 타겟을 만들고 **RBF 솔버 출력에 자동 연결**하는 툴을 개발했습니다.
- **결과**: 포즈별 수동 매칭 작업이 **버튼 한 번의 일괄 처리**로 대체됐습니다. 좌우 미러 생성, 임계값 이하 무주름 포즈 스킵, 기존 타겟 Skip/Overwrite 정책, 프레임 스텝 매핑 등 실사용 옵션을 갖췄고 전체 작업이 단일 Undo로 묶입니다.
- **키워드**: MetaHuman, PoseWrangler / RBF Pose Driver, Corrective Blendshape, `invertShape`, Alembic, Houdini Cloth

### 1-2. MetaHuman 페이셜 RBF 연결 자동화
`A00090_ConnectionBuilder`

- MetaHuman 페이셜 리그의 **RBF 솔버 → 드라이버 노드 → 블렌드셰이프** 어트리뷰트 연결을 **규칙(JSON) 기반으로 자동 결선**하는 툴입니다.
- 소스/타겟 리스트업 방식으로 **1→n, n→n 배치 연결**을 지원하고, 중간 노드(`WRK_intermediate`) 경유 결선과 연결 상태 검증(validate)/해제(disconnect)를 제공합니다.
- 규칙의 mapping 이름으로 **blendShape 코렉티브 타겟을 일괄 생성**합니다. 규칙 이름은 포즈 이름이라 옷·메시가 몇 벌이든 같은데, 마야의 **노드 이름은 씬에서 유일**해야 합니다. 그래서 타겟 메시는 `<메시>_<포즈>` 로 유일하게 만들고 **blendShape 웨이트 별칭(alias)만 포즈 이름으로 되돌려**, 여러 벌의 옷에 같은 규칙 세트를 그대로 적용하면서도 결선이 쓰는 주소(`<blendShape>.<포즈>`)는 유지되게 했습니다(별칭은 노드 단위라 blendShape 마다 같은 이름을 가질 수 있습니다).
- 수백 개 어트리뷰트를 손으로 잇던 작업을 규칙 파일로 관리해 **재현 가능·검증 가능**하게 만들었습니다.

### 1-3. MetaHuman 페이셜 데이터 유틸
`A00100_jsonEditor_MH`, `A00200_CSV_tool`, `A00320_ARKitCurveTool`

- **jsonEditor_MH** — MetaHuman 페이셜 정의 JSON의 정렬·편집 도구. RBF 솔버 세팅(보간 방식, 정규화 방식)을 데이터로 관리.
- **CSV_tool** — ARKit 페이셜 캡처 CSV를 Maya로 임포트해 커브로 굽는 도구.
- **ARKitCurveTool** — 언리얼의 `Add ARKit Curves to Skeleton` 동작을 분석해 **Maya 측에서 동일 결과를 재현**하는 코드/가이드로 정리.

### 1-4. 페이셜 컨트롤 구성 — blendShape 타겟 → 컨트롤러 어트리뷰트
`A00145_RigConnect` (Attribute 탭)

- blendShape의 타겟은 일반 어트리뷰트가 아니라 **`weight[]` 멀티에 걸린 별칭(alias)** 이라, 보통의 어트리뷰트 나열로는 첫 타겟 하나만 잡힙니다. `aliasAttr`에서 직접 읽어, **blendShape를 선택하면 Attribute·Connect 탭 양쪽에서 모든 타겟이 이름으로 나열**되게 했습니다.
- 고른 타겟을 **컨트롤러에 이름 있는 키어블 float 어트리뷰트로 복사**(접두/접미사 옵션, 타입·범위·기본값 보존)하고, Connect 탭으로 **컨트롤러 → blendShape 타겟**을 결선합니다.
- "이 수십 개 표정 셰이프를 리그 컨트롤로 노출" 하는 작업을, 어트리뷰트와 연결을 하나씩 손으로 추가하는 대신 골라서 복사하는 단계로 바꿨습니다 — 페이셜 컨트롤 리그 구성의 일상적 반복 작업입니다.

### 1-5. MetaHuman 스켈레톤 + 언리얼 RBF 세팅을 비(非)메타휴먼 아바타로 일반화
`A00270_skinMigrate`, `A00130_ControlRig`, `A00060_jointTool_V02`, `A00145_RigConnect`, `A00090_ConnectionBuilder`

- **목표**: MetaHuman에서 검증된 리그 접근 — 그 **본 구조**와 **언리얼 RBF(PoseWrangler) Pose Driver** 세팅 — 을 **다른 실사·카툰풍 아바타**에 그대로 세워, 언리얼까지 세팅합니다.
- 이 스크립트들은 **선택·JSON 규칙 기반이라 메타휴먼에 하드코딩돼 있지 않으므로**, 동일 파이프라인을 임의 캐릭터로 리타겟할 수 있습니다.
  - **커스텀 메시에 스켈레톤 얹기** — 조인트 구조를 생성·오리엔트(`A00060_jointTool_V02`, `A00130_ControlRig`의 부위별 매칭)하고, 토폴로지가 다른 메시로 **본 리매핑과 함께 스킨을 전이**(`A00270_skinMigrate`).
  - **리그 결선** — 매칭 / 컨스트레인트 / 어트리뷰트 복사 / 최근접 연결로 새 리그를 레퍼런스에 정렬(`A00145_RigConnect`).
  - **바디/관절 RBF** — 소스/타겟 리스트로부터 **RBF 솔버 → 드라이버 → 코렉티브** 어트리뷰트를 JSON 규칙으로 결선(`A00090_ConnectionBuilder`). 배포 규칙이 **바디-림**(`WRK_thigh / calf / lowerarm_l/r`) 코렉티브라, 동일한 RBF 결선을 **메타휴먼 얼굴을 넘어** 재사용합니다. 규칙 세트는 **버전 폴더**(`rules/v001`, `v002` …)로 나눠 두고 UI 에서 골라 쓰므로, 포즈 구성이 바뀌어도 옛 규칙을 덮어쓰지 않고 프로젝트별로 병행합니다.
  - **언리얼로** — 엔진에서 **PoseWrangler**로 RBF Pose Driver를 오소링해, 포즈 구동 변형이 대상 스켈레톤 위에서 엔진 내에서 살아 돌아가게 합니다.
- **결과**: MetaHuman 수준의 **포즈 구동 변형(RBF)** 을 **비메타휴먼 실사·카툰 아바타에서 반복 가능**하게 만들었습니다. 엔진 플러그인을 짜거나 캐릭터마다 RBF를 손으로 다시 세팅할 필요가 없습니다.
- **키워드**: RBF Pose Driver, PoseWrangler, 스켈레톤 리타겟, 토폴로지 간 스킨 전이, Control Rig, 아바타 비의존 리그 파이프라인, Maya → Unreal

### 1-6. Epic PoseWrangler(PoseDriverConnect) 플러그인 소스 직접 수정 — 부분 스켈레톤에도 RBF 프리셋 임포트
`PoseDriverConnect / epic_pose_wrangler` (Epic Games 공식 Maya 플러그인 포크)

> 1-5 를 **실제로 가능하게 만든 전제 조건**입니다. 언리얼이 제공하는 공식 플러그인의 파이썬 소스를
> 읽고, MetaHuman 이 아닌 아바타에서도 RBF 프리셋을 재사용할 수 있도록 직렬화 코드를 패치했습니다.

- **문제**: MetaHuman 에서 오소링한 RBF Pose Driver 프리셋(JSON)을 **다른 캐릭터 씬에 임포트하면 통째로 실패**합니다.
  원인은 델타 모드(`serializer_params.delta = true`)로 저장된 파일의 역직렬화 경로에 있었습니다 —
  `serializer_v1_2_0.Serializer.deserialize` 는 JSON 에 적힌 `driven_transforms`(무릎 back, thigh/calf twist
  corrective 같은 **헬퍼 조인트**) 목록을 **씬에 전부 존재한다고 전제**하고 현재 로컬 매트릭스를 수집한 뒤,
  포즈별 델타를 되돌릴 때 `current_driven_transforms[name]` 을 무조건 참조합니다.
  즉 **헬퍼 조인트가 하나라도 빠진 커스텀 스켈레톤**에서는 임포트가 예외로 중단되어, 프리셋을 부분적으로도
  적용할 수 없었습니다. (MetaHuman 표준 스켈레톤 전체를 그대로 들고 있는 씬에서만 동작)
- **한 일** — 원본 동작을 깨지 않는 **최소 침습 패치** 3단계:
  1. **존재하지 않는 driven 필터링** — 솔버 데이터를 읽는 시점에 `driven_transforms` 를 `cmds.objExists` 로
     걸러 **씬에 실존하는 조인트만** 남깁니다. → 현재 포즈 매트릭스 수집
     (`utils.get_local_matrix_without_joint_orient`) 단계의 예외 제거.
  2. **포즈 델타 재계산 루프 방어** — 포즈별로 `delta × rest` 를 곱해 절대 매트릭스를 복원하는 루프에서도
     씬에 없는 driven 은 건너뛰어 `KeyError` 를 막습니다.
  3. **빈 솔버 스킵** — 필터 결과 driven 이 **0 개가 된 솔버**를 표시해 두었다가 `RBFNode.create_from_data`
     단계에서 건너뛰고 어떤 솔버를 무시했는지 로그로 남깁니다. → **구동 대상이 없는 껍데기 RBF 솔버 노드가
     씬을 오염시키는 것**을 방지.
- **부가 정비**: 커스텀 빌드임을 한눈에 알 수 있도록 창 타이틀에 `[JUN]` 태그를 붙이고, 셸프에 걸 수 있는
  2줄짜리 실행 스니펫을 추가했으며, 실제 하체 RBF 프리셋(`calf_l_UERBFSolver` — 무릎/트위스트 코렉티브
  5개 driven)을 **회귀 확인용 샘플 JSON** 으로 리포에 커밋했습니다. 벤더 원본을 첫 커밋으로 두고
  수정 이력을 git 으로 관리해 **엔진 플러그인 업데이트 시 내 패치만 골라 재적용**할 수 있게 했습니다.
- **결과**: MetaHuman 에서 검증한 RBF 세팅을 **헬퍼 조인트 구성이 다른 비메타휴먼 아바타에 그대로 임포트**해
  **있는 조인트에 대해서만 솔버가 재구성**됩니다. 캐릭터마다 프리셋을 손으로 잘라내거나 RBF 를 다시
  세팅할 필요가 없어졌습니다.
- **의의**: 서드파티(엔진 벤더) 플러그인이라도 **소스를 읽고 델타 기반 포즈 데이터의 매트릭스 수학**
  (rest 포즈 로컬 매트릭스 × 포즈 델타)을 이해하면 파이프라인에 맞게 고칠 수 있다는 사례입니다.
  블랙박스로 두고 우회하는 대신 **원인 지점을 특정해 최소한으로 수정**했습니다.
- **키워드**: PoseWrangler / PoseDriverConnect, RBF Pose Driver, 델타 직렬화(serializer), `cmds.objExists` 가드,
  MMatrix 델타 복원, 서드파티 플러그인 포크·패치 관리, MetaHuman → 커스텀 아바타

## 2. 언리얼 엔진 노드 생성 툴 (Maya → UE 브릿지)

> 공통 아이디어: 언리얼 그래프의 노드는 **텍스트로 복사/붙여넣기가 가능**합니다.
> Maya 씬의 리그 정보를 읽어 **언리얼 노드 텍스트를 생성 → 클립보드 복사 → UE 그래프에 Ctrl+V** 하면
> 수십~수백 개의 노드가 정확한 값과 위치로 한 번에 만들어집니다. 이 원리로 3종의 변환기를 만들었습니다.

### 2-1. Maya 조인트 → 언리얼 KawaiiPhysics 변환기
`A00080_KWI_creator` (V01 → V02 standalone → **V03 in-Maya**)

- Maya에서 선택한 **타겟 루트 본 목록**을 읽어, 본 개수만큼 **KawaiiPhysics AnimGraph 노드**(base / 세팅 / LOD 분기)를 템플릿 치환으로 생성하고, 노드 위치까지 자동 배치해 그래프에 붙여넣습니다.
- **Constraints 탭**: KawaiiPhysics **Bone Constraints Data Asset** 내용을 생성. 씬에 존재하는 본 쌍만 필터링하고 인덱스 제로 패딩을 맞춰 그대로 데이터 애셋에 반영됩니다.
- **진화 과정**: 텍스트 생성 로직(core)은 유지한 채 UI만 standalone Qt 앱 → Maya 내부 PySide 툴로 재구성. 본 목록을 파일이 아니라 **Maya 씬 선택에서 바로** 받도록 개선했습니다. (core/ui 분리 설계의 실효 사례)
- **결과**: 헤어·의상·액세서리의 흔들림 물리를 본 단위로 손수 세팅하던 작업을 **본 리스트만 넘기면 끝나는 작업**으로 만들었습니다.

### 2-2. Maya 컨스트레인트 → 언리얼 Control Rig 컨스트레인트 변환기
`A00260_ConstraintConverter`

- Maya 씬에 걸린 **컨스트레인트 세팅(타입/타겟/웨이트)** 을 읽어 언리얼 **Control Rig의 Parent / Position / Rotation Constraint 노드 텍스트**로 변환합니다.
- 축별 필터(Translate/Rotate 축 On/Off), 노드 접힘(collapsed) 출력, 4개마다 줄바꿈하는 **자동 가로 배치**, 노드 간 **ExecutePin 연결(RigVMLink)** 까지 생성해 붙여넣는 즉시 실행 가능한 그래프가 나옵니다.
- **결과**: Maya에서 검증한 리그 구속 관계를 언리얼에서 다시 손으로 짤 필요가 없어졌습니다.

### 2-3. Maya 오브젝트 → 언리얼 Control Rig Item Array 변환기
`A00350_ArrayCreator`

- 리스트에 담은 Maya 오브젝트를 그 순서대로 언리얼 Control Rig의 **Item Array 노드(`TArray<FRigElementKey>`)** 텍스트로 생성 → 클립보드 복사.
- Element Type(Bone/Control/Null/Curve/Socket 등) 지정, 순서 조정(Up/Down/Reverse)을 지원합니다. 체인을 끝→루트로 선택했을 때 한 번에 뒤집는 **Reverse**는 공용 위젯 레벨의 옵션으로 만들어 다른 툴에도 재사용됩니다.

### 2-4. 【사례】 Maya splineIK 세팅을 언리얼로 그대로 이식 + 런타임 물리 구동
`A00350_ArrayCreator` + `A00260_ConstraintConverter` + `A00145_RigConnect`

> 위 변환기들을 **낱개로 쓰지 않고 하나의 파이프라인으로 엮은 실사용 사례**입니다.
> "Maya에서 만든 splineIK 리그를 언리얼에서 **물리로 살아 움직이게** 한다"가 목표였습니다.

- **문제**: **양 끝점이 항상 고정되어야 하는 조인트 체인**을 언리얼에서 흔들어야 했습니다. 체인 본에 물리(KawaiiPhysics / Physics Asset)를 직접 걸면 **끝점 고정이 풀려** 원하는 거동이 나오지 않습니다. 게다가 Maya에서 세팅한 splineIK 거동을 엔진에서 다시 손으로 재현하는 것도 부담이었습니다.
- **접근 — 물리로 흔들 대상을 체인이 아니라 "커브의 제어점"으로 옮김**
  1. **Maya**: 조인트 체인과, 그 체인을 구동할 **splineIK 커브**를 세팅하고, 커브의 **control vertex 위치마다 조인트를 생성**했습니다(이하 **CV 조인트**). 체인 전체 대신 **소수의 CV 조인트만** 물리 대상이 되므로, **양 끝 CV를 고정하면 끝점 고정이 구조적으로 보장**됩니다.
  2. **CV 조인트 부착**: CV 조인트가 캐릭터의 특정 위치에 따라다니도록 컨스트레인트로 붙이되, 붙일 대상을 눈대중으로 고르는 대신 **`A00145_RigConnect`의 Skin Weight to Constraint** 기능으로 **스킨 웨이트에서 부착 대상과 웨이트를 그대로 유도**했습니다. → 메시가 실제로 따르는 본에 CV가 붙습니다.
  3. **언리얼 — 데이터 이식**: **`A00350_ArrayCreator`** 로 조인트 체인과 CV 조인트 목록을 **Control Rig의 Item Array 노드 텍스트**로 생성해 붙여넣고(splineIK 노드가 요구하는 순서 있는 본 배열), **`A00260_ConstraintConverter`** 로 CV 조인트에 걸린 **컨스트레인트 관계를 Control Rig 컨스트레인트 노드로 변환**했습니다. → Maya에서 검증한 결선을 엔진에서 다시 짜지 않습니다.
  4. **언리얼 — 구동**: CV 조인트에 **KawaiiPhysics 또는 Physics Asset**을 걸어 흔들리게 하고, **Control Rig에서 splineIK를 세팅**해 **CV 조인트가 흔들리면 조인트 체인이 그대로 따라 휘도록** 연결했습니다.
- **결과**: Maya에서 오소링한 splineIK 거동이 **언리얼에서 런타임 물리로 살아 움직이면서도 양 끝은 계속 고정**됩니다. 애니메이션을 구워 넣는 방식이 아니라 **엔진 내 실시간 시뮬레이션**이라 어떤 동작에도 반응합니다.
- **의의**: 자체 제작한 툴 3종(**Item Array 생성 · 컨스트레인트 변환 · 스킨웨이트→컨스트레인트**)을 조합해, **Maya 리그 데이터 → 언리얼 Control Rig + 물리**로 이어지는 경로를 **수작업 재구축 없이** 완성했습니다.

```
[Maya]                                    [Unreal]
 조인트 체인  ─┐                            조인트 체인 (동일 스켈레톤)
              │ splineIK                        ▲  splineIK (Control Rig)
 splineIK 커브 ┘                                 │
      │ control vertex 위치                     CV 조인트
      ▼                                          ▲  KawaiiPhysics / Physics Asset
  CV 조인트  ── A00145 Skin Weight to Constraint ─┤   (양 끝 CV 고정 → 끝점 고정 유지)
      │                                          │
      └── A00350 Item Array ─────────────────────┤  ← 체인/CV 본 배열 텍스트
      └── A00260 Constraint Converter ───────────┘  ← 컨스트레인트 관계 노드 텍스트
```

- **키워드**: splineIK, Control Rig, KawaiiPhysics, Physics Asset, 런타임 2차 모션, 양 끝 고정 체인, 스킨 웨이트 기반 부착, Maya → Unreal 리그 데이터 변환

## 3. 리깅 자동화 (캐릭터 리그 · 스키닝 · 셰이프)

### 3-1. 함수 구동 트위스트·디폼 리그 에셋 — `A00170_driverTool`로 제작

툴을 만드는 데서 그치지 않고, 그 툴로 **촉수·뱀** 같은 실사용 리그 에셋을 세웠습니다.

- **개념 — 드라이버에 함수를 "신호처리"하듯 얹기**: 계층으로 쌓은 **드라이버(null) 노드의 Translate / Rotate / Scale** 어트리뷰트에, 원하는 수학 함수를 **신호를 처리하듯 적용**합니다. 드라이버는 조인트 체인에 연결되어 있어, 체인의 변형을 **함수 단위로, 그리고 additive(중첩) 방식으로** 표현합니다. Stretch 탭이 선형·시그모이드 함수를 driven 네트워크로 만들고 그 출력을 **원래 값 위에 additive로** 얹기 때문에, **여러 함수를 한 체인에 겹쳐 쌓아** 복합 거동을 구성할 수 있습니다.
- **체인 트위스트 — splineIK 한계 극복**: 조인트 체인의 **처음부터 끝까지 트위스트가 얼마나 분배될지**를 함수로 지정합니다. up 벡터 하나로 트위스트를 만들 때 생기는 **splineIK의 한계**(전 구간에 걸친 점진적·과도 트위스트를 깔끔히 주기 어려운 문제)를, 함수 기반 분배로 극복합니다. 촉수·뱀처럼 **길게 감기고 비틀리는** 리그에 특히 유효합니다.
- **매트릭스 컨스트레인트 대비 경쟁력**: 트랜스폼을 그대로 복사·구속하는 **매트릭스(offsetParentMatrix) 방식과 달리**, 값이 체인을 타고 전파되는 **모양 자체를 함수로 설계**합니다. 시그모이드는 수렴 상·하한(threshold, 0 밑으로 안 내려감)과 급격함을 갖고, 이 파라미터가 **드라이버 오브젝트의 씬 어트리뷰트로 노출**되어 리그를 다시 짜지 않고도 **씬에서 실시간으로 falloff를 조율·애니메이트**할 수 있습니다. 결과적으로 "딱딱한 구속"이 아니라 **아트 디렉션 가능하고, 겹쳐 쌓이며, 실시간 튜닝되는** 변형을 얻습니다.
- **언리얼 임포트 레디 — 의도한 대로 재생**: 이 셋업은 Maya 전용 구성이 아니라 **실제 조인트 체인**을 구동하므로, 그 결과 스켈레탈 애니메이션이 **언리얼로 임포트되면 의도한 그대로 재생**됩니다. (라이브 Control Rig로 이식하진 않았지만, 드라이버 함수 네트워크가 **조인트/스켈레톤 애니메이션으로 베이크되어** 나가므로 엔진에서 그대로 살아 움직입니다.) 게임 파이프라인 관점에서 **엔진 레디**한 리그입니다.

```
Default Distance 어트리뷰트 (driver 신호 x)
        │  A00170 Stretch:  f(x) = 선형 / 시그모이드 (threshold·sharpness = 씬 어트리뷰트)
        ▼
  드라이버 null 계층  (T / R / S,  원래 값 위에 additive)
   null_0 → null_1 → null_2 → … → null_n     ← 함수를 겹쳐 쌓음(레이어)
        │  구동
        ▼
  조인트 체인  jnt_0 → jnt_1 → … → jnt_n      → 루트→팁 점진 트위스트 (splineIK up-vector 한계 극복)
        │  FBX 스켈레탈 애니메이션으로 베이크
        ▼
  Unreal:  임포트 → 의도한 대로 애니메이션 (엔진 레디)
```

- **키워드**: 드리븐 함수 리그, additive 함수 레이어링, 체인 트위스트 분배, splineIK up-vector 한계 극복, 시그모이드 falloff, 실시간 어트리뷰트 제어, vs 매트릭스 컨스트레인트, 촉수·뱀 리그, 언리얼 임포트 레디

- 키 복사/붙여넣기(축 반전 포함, **원본 하나 → 대상 전부** 뿌리기, **T/R/S × XYZ + 커스텀 채널 선택**), **L/R 컨트롤러 키 미러**, 포즈 키(6축), Offset & Hold, 베이크(Smart bake 포함), **Follow(타겟 매치 베이크)**, Graph Editor 자동 프레이밍(선택 시 현재 프레임 ±마진으로 확대) 등 애니메이터 반복 작업을 한 창에 통합.
  - **키 복사가 커스텀 채널까지** — 채널 선택 UI 가 T/R/S 9축만 다뤄, 축을 하나라도 골라내면 `ikBlend`·페이셜 슬라이더 같은 **사용자 어트리뷰트의 키가 조용히 빠졌습니다**(9축을 전부 켜 둔 기본 상태에서만 멀쩡해 보여 발견이 늦는 종류의 문제). Base 의 **채널박스 노출 키 가능 채널**을 나열해 9축과 함께 고르도록 했습니다.
  - 이때 노드 단위 `pasteKey(attribute=[...])` 는 클립보드 커브를 **이름이 아니라 순서로** 맞춰(headless 로 확인) 키 없는 채널이 섞이면 **엉뚱한 채널에 커브가 들어갑니다** — 채널 단위 copy/paste 로 돌려 그 오염을 없애고, 없거나 잠긴 채널은 건너뛰되 사유를 로그에 남깁니다.
- 레거시 MEL/SmartLayer의 베이크 알고리즘을 분석·문서화하고 **네이티브 API 기반으로 이식**해 결과 동등성과 속도를 함께 확보했습니다.
- **Stagger Offset — 순차 지연(팔로우스루/웨이브)을 슬라이더로 오소링**: 리스트업한 컨트롤러들의 지정 구간 키를 **리스트 순서 × N프레임**만큼 계단식으로 밀어, 꼬리·머리카락·천처럼 앞 요소를 뒤 요소가 지연해 따라오는 움직임을 만듭니다. 값은 **슬라이더로 실시간 조절**되며 **누적되지 않습니다**(항상 원래 위치 기준 재계산).
  - **실시간 편집과 Undo를 양립시킨 설계**: 드래그 중에는 undo 큐에 기록하지 않아 항목이 쌓이지 않고, 조작이 **멎는 순간** 그때까지의 결과를 **한 항목으로 정착(settle)** 시킵니다. 기록 직전 반드시 마지막 기록 상태로 되돌린 뒤 기록해(undo는 *역연산을 현재 상태에 적용*하므로) **Ctrl+Z 한 번이면 조작 직전으로** 정확히 돌아갑니다.
  - **키 이동을 상대 이동만으로 처리**해 커브를 재생성하지 않으므로 **탄젠트·인피니티·애님 레이어 소속이 보존**됩니다. 사용자가 씬에서 Undo를 눌러 세션의 가정이 깨지는 경우까지 **탐침 키로 감지**해 오동작을 막았습니다.
  - 동작 규칙은 **headless(mayapy) 59개 시나리오로 검증**했습니다(비누적·구간 밖 키 보존·탄젠트 보존·undo 복귀 등).
- **Euler Filter — "구간만" 오일러 필터**: 마야의 `Curves > Euler Filter` 는 컨트롤러의 **키가 찍힌 전 구간**을 한꺼번에 처리해서, 회전이 뒤집힌 **한 구간만** 펴고 나머지는 그대로 두는 작업이 불가능했습니다. 대상(리스트)과 구간(Start/End)을 지정해 **그 구간 안의 회전 키만** 펴도록 만들었습니다.
  - **직접 구현 대신 마야의 필터를 정확히 겨냥**: headless(mayapy) 검증 결과 `filterCurve -f euler` 는 `startTime`/`endTime` 을 **실제로 존중**했습니다(메뉴가 전 구간을 처리하는 건 MEL 이 구간을 안 넘겨서). 그래서 마야의 오일러 수식·탄젠트 처리를 그대로 쓰면서 구간만 제한해, **`rotateOrder` 가 `xyz` 가 아닌 리그(`zxy` 등)에서도 결과가 마야와 일치**합니다.
  - **앵커(Anchor) 옵션으로 앞쪽 이음매 제거**: 마야 필터는 *구간 안 첫 키*를 기준으로 삼기 때문에, 플립이 Start 직전에서 시작하면 **아무것도 고쳐지지 않습니다**. 필터 구간을 **Start 직전 키까지 넓혀** 그 키를 기준으로 삼으면, 기준 키는 값이 바뀌지 않으므로 **"구간 밖은 그대로"** 를 지키면서 앞쪽 애니메이션과 매끄럽게 이어집니다.
  - 필터 전/후 값 스냅샷을 비교해 **실제로 바뀐 키 수**를 세고, 구간 한정 필터의 필연적 결과인 **End 경계 이음매**를 사용자에게 먼저 알립니다.
  - **작업 흐름 그대로의 원버튼**: 애니메이터의 실제 조작은 "컨트롤러 몇 개를 고르고 그래프 에디터에서 문제 구간을 드래그" 로 끝나는데, 그걸 다시 리스트와 Start/End 칸으로 옮겨 담는 게 번거로웠습니다. **씬 선택 = 대상**, **선택한 키의 앞/뒤 프레임 = 구간**으로 두 감지를 한 번에 처리하는 버튼을 추가했습니다. 감지한 값은 리스트·입력칸에도 **되채워** 무엇을 어느 구간으로 처리했는지 남기고, **키를 고르지 않았으면 실행하지 않습니다**(전 구간을 조용히 건드리는 쪽이 더 위험하므로).
- **Fill Keys** 는 지정 구간의 **모든 프레임에 키를 채웁니다**(애니메이션 레이어 지정 가능). 기존 키는 그대로 두므로, 손으로 잡은 애니메이션을 프레임 단위로 고정해 두고 이후 편집을 얹을 수 있습니다.
- **애니메이터가 실제로 쓰는 커브 필터** — 스무딩(가우시안), 인텐시티(**구간 평균**을 기준으로 진폭을 조절해 위아래로 밀리지 않습니다), 인터폴레이트(구간 양 끝 키를 잇는 이징 곡선으로 중간 키를 끌어당깁니다). 회전은 **쿼터니언으로 묶어** 필터링하고 오일러로 되돌릴 때 원래 값에 가장 가까운 해를 골라 짐벌락 근처의 ±360 점프를 없앴습니다. 값은 커브를 재생성하지 않고 `keyframe -e -valueChange` 로만 써서 **탄젠트·인피니티·애님 레이어 소속이 보존**되고, 양방향 슬라이더는 Stagger Offset 과 같은 settle 커밋이라 **드래그 한 번 = undo 한 번**이며 놓으면 슬라이더가 가운데로 돌아와 한 번 더 적용할 수 있습니다. 리스트업 단계가 없습니다 — **그래프 에디터에서 고른 키**에 바로 적용되고, 아무것도 고르지 않았으면 전 구간을 조용히 건드리는 대신 실행을 거부합니다.
- **절차적 노이즈를 "키로" 만듭니다 (Create > Noise)** — 손떨림·깜빡임처럼 불규칙한 흔들림을 손으로 찍지 않고, 결정론적이고 **이음매 없이 반복되는** 노이즈 노드를 만들어 리그 어트리뷰트에 연결합니다. 종류(Value/Perlin/Simplex/Worley/Ridged)와 부드러움·오프셋·최소/최대를 **한 노드에 모아** 실시간으로 조절하고, 노드는 몇 개든 만들어 각각 다른 설정으로 쓸 수 있습니다.
  - **"그래프 에디터에서 보여야 한다"는 요구 하나가 설계를 결정했습니다**: 마야의 그래프 에디터는 **애니메이션 커브만 그립니다**. 표현식이나 커스텀 플러그인 노드로 매 프레임 계산하는 — 가장 먼저 떠오르는 — 설계는 값은 맞지만 **곡선이 보이지 않아** 요구의 절반을 버리게 됩니다. 그래서 노이즈를 **진짜 애니메이션 커브로 굽고, 설정이 바뀌면 즉시 다시 굽는** 구조를 택했고, 성립 조건인 "다시 굽는 속도"를 먼저 측정해(1000키 재기록 3.4ms, 약 295fps) 실시간 슬라이더가 가능함을 확인한 뒤 진행했습니다. 결과적으로 재생 중 계산 비용이 **0**이고(커브 조회일 뿐), 플러그인 배포가 필요 없으며, 애니메이터가 만들어진 커브를 **직접 손볼 수도** 있습니다.
  - **"부드러움"을 스펙트럼 지수로 정의**했습니다. 옥타브별 진폭을 `1/f^β` 로 가중하면 β 가 곧 "프레임과 프레임 사이 값이 얼마나 변하는가"가 됩니다(신호처리에서 말하는 백색·분홍·갈색 노이즈와 같은 정의). 덕분에 **노이즈 종류와 부드러움이 서로 독립**이라 종류를 추가해도 부드러움 로직은 건드릴 필요가 없습니다.
  - **LUT 파일을 만들지 않기로 한 것도 측정 결과입니다.** 미리 구운 표를 파일로 두는 편이 빠를 것 같았지만, 실제로는 생성이 5ms짜리 1회성 작업이라 디스크에서 읽어 파싱하는 것보다 빠르거나 비슷했습니다. 대신 결정론은 파일이 아니라 **직접 구현한 정수 해시**로 보장해(표준 난수 모듈은 구현에 따라 결과가 달라질 수 있습니다) 어느 PC에서 열어도 같은 노이즈가 나옵니다.
  - **실시간 편집과 Undo의 양립**에서 API의 함정을 만났습니다. 커브 값을 빠르게 덮어쓰는 API 호출은 **되돌리기 정보를 남기지 않아**, 그대로 두면 "드래그 한 번 = Ctrl+Z 한 번"이 성립하지 않습니다. 그래서 **미리보기는 그 빠른 경로로, 확정은 되돌리기가 되는 경로로** 갈라 둘 다 제 역할을 하게 했습니다.
- **Follow 의 타깃으로 메시 버텍스**를 받습니다. 컴포넌트에는 `worldMatrix` 가 없으므로 버텍스의 **위치 + 노말**로 프레임을 구성했고, 컴포넌트 위치는 임의 시간으로 질의할 수 없어(`getAttr(time=)` 이 적용되지 않음) 프레임을 실제로 이동하며 평가합니다.

### 4-2. 시뮬레이션 대신 관성을 키로 굽기
`A00410_SecondaryMotion`

- **문제**: 꼬리·머리카락·천에는 팔로우스루가 필요한데, 마야의 시뮬레이션 솔버(`nucleus`/nHair/nCloth)는
  결과를 얻으려면 **시작 프레임부터 순차 재생**해야 합니다. 스크럽이 안 되고, 파라미터를 바꿀 때마다
  처음부터 다시 재생해야 하며, 게임 에셋으로 쓰려면 결국 별도 베이크 단계가 또 필요합니다.
- **한 일**: 언리얼 **KawaiiPhysics** 의 관성 모델(부모에서 먼 자식일수록 원래 자리에 남으려 하고, 가까운
  자식일수록 부모를 더 따라간다)을 구간 전체에 대해 프레임마다 계산해 **키로** 기록합니다. Live Preview 는
  구간 전체를 계산해 프리뷰 레이어에 넣으므로 바로 스크럽할 수 있고, Apply 하면 그 레이어가 그대로 최종
  **override 애님 레이어**가 됩니다 — 원본 애니메이션은 남아 있고 **레이어 weight 로 강도를 조절**하거나
  (0 = 원본, 1 = 결과) 레이어만 지우면 원복됩니다.
- **수식이 정확해야 했던 지점**: 조인트의 로컬 회전은 `R × jointOrient` 인데 일반 트랜스폼은
  `rotateAxis × R` 입니다. 같은 방식으로 합성하면 한쪽이 깨집니다. 체인 노드의 부모를 "앞 체인 노드"로
  가정하는 것도 중간에 오프셋 그룹이 낀 리그에서 깨지므로, 실제 부모를 노드마다 확인합니다.

### 4-3. 주기함수로 만드는 바람 흔들림
`A00390_WindTool`

- 체인의 조인트마다 **위상만 순번만큼 미룬** 같은 싸인 파형을 넣어 체인이 순차적으로 흔들리게 합니다.
  출력은 두 가지 — **Curve** 는 키를 굽고, **Node** 는 드라이버 null + 노드망을 만들어 실시간 재생하며
  `windPeriod / windAmplitude / windOffset / windSpeed` 를 어트리뷰트로 노출합니다. 다시 굽지 않고
  씬에서 룩을 조절할 수 있습니다.
- **디포머와 같은 `windEnvelope` [0, 1]** 를 모든 드라이버에 두어 0 = 영향 없음 · 0.5 = 절반 ·
  1 = 완전 적용으로 세기를 조절하고, 키를 걸어 **바람을 페이드 인/아웃** 시킬 수 있습니다.
  파형 값이 진폭에 정비례한다는 점을 이용해 **드라이버당 곱셈 노드 하나**로 구현했습니다 —
  조인트나 CV 마다 노드를 늘리지 않습니다.

- **`A00390_WindTool_V02` — Chain Wave Lite** 는 같은 종류의 움직임을 **커브·ikHandle·프록시 없이**
  각도만으로 만듭니다(루트가 100개 넘을 때를 위해). 회전축은 두 가지로 정합니다 —
  **월드 `Sway Axis`**(체인 방향 × 월드 축으로 계산, 조인트 orient 와 무관)와
  **오브젝트 `Rotate Axis`**(각 노드의 `rotate` 채널 **하나만**). 후자를 켜면 전자는
  UI 뿐 아니라 **계산 분기 자체에서 빠집니다** — "비활성인데 값은 쓰이는" 상태를 만들지
  않으려고, `Sway Axis` 를 X/Y/Z 로 바꿔 가며 결과 회전값이 **완전히 동일**한 것까지 실측했습니다.
  부수적으로 **더 가볍고**(축이 기울면 노드마다 붙던 쿼터니언 노드 3개가 곱셈 1개로 — 비스듬한
  조인트 9 체인에서 102→84 노드) **나머지 두 축을 애니메이터가 계속 쓸 수 있습니다.**
  단, 이 방식은 체인 노드들이 **같은 방향으로 orient** 돼 있다는 전제가 필요해(각도 차분이 월드
  각도로 누적되어야 하므로) 그 한계를 툴팁과 문서에 명시했습니다.
- 드라이버 로케이터는 **constraint 없이** 루트 본/컨트롤러의 **월드 위치를 따라갑니다**.
  `worldInverseMatrix` 를 쓰면 자기 `translate` 를 되읽어 사이클이 되므로 **`parentInverseMatrix`**
  로 부모 공간을 상쇄해 `multMatrix → decomposeMatrix → translate` **노드 2개**로 끝냈습니다.
  사이클이 되는 배치는 하나뿐(드라이버가 루트의 조상)이라 그 경우만 **연결을 거부하고 사유를
  로그에 남깁니다.** 생성물은 종류별로 그룹을 나눠(로케이터 / 디버그 커브) 아웃라이너에
  번갈아 쌓이지 않게 했습니다.
- **파장을 숫자가 아니라 체인에서 받아 옵니다** (`Auto Period`, 기본 ON). 예전에는 손으로 적은
  파장을 모든 체인이 그대로 써서, 짧은 체인에는 파형이 반 토막만 · 긴 체인에는 몇 주기가
  실렸습니다. 이제 체인마다 `windWavelength = 그 체인의 길이` 라 **루트에서 끝까지 딱 한 주기**
  가 실립니다(진폭의 최댓값·최솟값이 각각 한 번). 여기서 길이는 루트-끝 **직선 거리가 아니라
  노드를 따라간 경로 길이**입니다 — 파형의 위상을 매기는 값이 이미 같은 누적 거리라, 두 척도를
  일치시키면 **굽은 체인도 굽은 길이 그대로** 한 주기가 됩니다. 노드망은 한 줄도 늘지 않았고
  (`lambda` 상수만 바뀝니다), 빌드 뒤에도 `windWavelength` 는 라이브 어트리뷰트로 남아
  Auto 는 **시작값만** 정합니다. 굽은 체인이 직선 거리 8.544 가 아닌 **경로 11.0** 을 받는 것,
  파형 양끝 값이 같고 최대·최소가 한 번씩인 것을 mayapy 헤드리스로 실측했습니다.

- **재생이 왜 느린지 끝까지 파고들어 144~202배로 되돌린 사례** (`A00390_WindTool_V03`).
  체인이 30개를 넘으면 재생이 30fps 아래로 떨어졌습니다. 노드가 많아서라고 짐작하기 쉬웠지만
  **헤드리스 mayapy 로 하나씩 분리해 재 보니 원인은 노드망이 아니었습니다** — 드라이버마다
  붙던 `expression` 하나가 매 프레임 `getAttr -time` 을 시작 프레임부터 현재 프레임까지
  반복 호출하고 있었고, 그것이 **재생 비용의 99.8%** 였습니다(30체인 58.7ms → 표현식만
  지우면 0.10ms). "재생할수록 느려진다"는 증상, 조인트 수와 무관하고 체인 수에만 비례하는
  것, Evaluation mode 를 바꿔도 같은 것이 전부 이 하나로 설명됐습니다.
- 고칠 때 **상수 속도의 적분은 곱셈 한 번**이라는 점을 이용해 표현식을 노드 3개로 바꿨고,
  그래서 **기존 씬의 결과 회전값이 한 자리도 달라지지 않습니다**(실측 `0.000e+00`).
  속도에 키를 건 경우에는 커브의 **키 데이터를 직접 읽어** 구간 적분하는 방식으로 라이브를
  유지했습니다. 이때 **표현식은 내용보다 개수가 비용**이라는 것을 측정으로 발견해
  (드라이버마다 두면 5.84ms, 하나로 합치면 1.38ms) 씬에 표현식을 하나만 둡니다.
  20~200체인에서 **144~202배**, 재생 구간에 따라 느려지던 것도 사라졌습니다.
- 함께 넣은 **체인 mute** 는 "값을 0으로 만드는 것과 평가를 막는 것은 다른 일" 이라는 점을
  분명히 한 기능입니다. 기존 `windEnvelope=0` 은 스윙에 0을 곱할 뿐이라 성능이 전혀
  변하지 않았고(62.97→63.18ms), `nodeState=Blocking` 으로 **rest 자세를 만든 뒤 고정**해야
  했습니다. `HasNoEffect` 는 "계산 없이 통과" 라 rest 를 만들지 못한다는 것도 실측으로
  가렸습니다. 다만 근본 원인을 고친 뒤에는 이 기능의 성능 이득이 1.3배뿐이라,
  **성능이 아니라 "보고 싶은 체인만 흔들리게 한다"는 작업 편의로 자리매김**했습니다.

  그 역할을 넘겨받습니다(분기 처리도 재귀 하강이라 자식이 여럿이면 갈래마다 스택이 갈라집니다).
  컨스트레인트는 parent/point/orient/scale 을 고를 수 있게 하되, **parent 와 point/orient 를 함께 켜면
  같은 채널을 두 컨스트레인트가 다툰다**는 점을 headless 로 확인해(마야가 두 번째를 `Object is already
  connected` 로 거부) 막지는 않고 경고로 알립니다 — 쓸모 있는 조합은 `parent + scale` 입니다.
- **`A00050_uvTool`**, **`A00030_quickTool`**, **`A00330_NamingTool`**(레거시 네이밍 툴 이식 + Quick Rename), **`A00310_SearchTool`**(타입·이름 기반 선택), **`A00360_SortTool`**(월드 X/Y/Z·이름·타입 기준 정렬 및 아웃라이너 재정렬).

## 6. 파이프라인 인프라 · 공용 프레임워크 (툴을 찍어내는 툴)

낱개 스크립트가 아니라 **툴을 지탱하는 공통 기반**을 함께 설계했습니다.

- **공용 Framework**
  - 재사용 위젯(리스트/버튼/콤보 등)과 **14종 컬러 테마(qss)** 통일 — 21개 Qt 툴의 UI를 카테고리별로 정리.
  - **UUID 기반 오브젝트 리스트** — 이름 중복·리네임·리페어런트에도 리스트↔씬 선택이 흔들리지 않도록 전 툴 공용 위젯을 개선(18개 툴에 동시 적용).
  - 공용 `undo_chunk` — 반복 씬 변경을 **Ctrl+Z 한 번**으로 되돌리도록 규약화.
  - `PathManager`(읽기/쓰기 경로 분리), Maya 메인 윈도우 부모 설정, 모듈 리로더.
  - 반복되는 마야 함정은 **프레임워크에서 한 번에** 정리합니다. 셰이프 확정 공용 헬퍼를 만들어 `extendToShape` 패턴을 **툴 6종에서 일괄 교체**했고, 셰이프 노드가 둘 이상인 메시에서 나던 `kInvalidParameter: Object is incompatible` 실패를 없앴습니다.
- **배포/설치 체계**
  - **드래그&드롭 셸프 설치** — `.py` 파일을 Maya 뷰포트에 끌어놓으면 아이콘 셸프 버튼이 설치되는 방식. 툴별 고유 파일명 규칙으로 `sys.modules` 캐시 충돌 문제를 해결.
  - **PyInstaller 기반 `.exe` 빌드**, 릴리스 빌더(툴 + 프레임워크 + 문서 자동 패키징), 작업표시줄 아이콘 처리.
- **스탠드얼론 파이프라인 유틸**
  - `A00210_FileManager` — 파일/버전 매니저. 파일 간 **참조 관계를 노드 그래프(Lineage)로 시각화**, Remote(Git) ↔ Local(NAS) 소스 모드, **폴더 구조 캡처/재생성**(파일까지 잡아 **0바이트 플레이스홀더**로 되살리되 이름에 표식을 붙여 원본과 구분 — 실제 씬 파일은 공유하지 않는다는 원칙 유지), 썸네일·로그 기록. (`A00211_RefLineage`로 Maya 씬의 레퍼런스 관계를 그대로 내보내기)
  - `A00220_BackupTool` — 지정 파일 **주기적/저장 시점 자동 백업**(크래시 대비).
  - `A00240_PathTool` · `A00370_ToolLauncher` · `A00230_StartupTool` — 자주 쓰는 경로/툴을 버튼·프로파일로 즉시 실행, Windows 부팅 시 자동 실행. **PC가 바뀌어도 경로가 자동 재매핑**되도록 처리.
- **문서화** — 툴마다 사용 가이드 문서 + CHANGELOG + 버전 파일을 유지하고, 일일 작업 로그(WORKLOG)를 운영했습니다.

## 7. 이 작업에서 강조하고 싶은 점

1. **DCC를 넘나드는 문제 해결** — Maya, Unreal, Houdini(캐시)를 하나의 흐름으로 잇는 툴을 만들었습니다. 특히 언리얼 노드를 텍스트로 생성하는 접근은, 엔진 플러그인 없이도 대량의 그래프 세팅을 자동화할 수 있는 실용적인 해법이었습니다.
2. **레거시 자산의 현대화** — 사내에 흩어져 있던 MEL/단일 파일 스크립트들을 분석해 Qt 툴로 통합·이식하면서, 기존 동작의 동등성을 검증하고 문서로 남겼습니다.
3. **아티스트 우선 설계** — 툴의 성패는 UI에서 갈린다고 봅니다. 항상 위(Pin) 토글, 접이식 섹션, 정렬/검색, 색상 커스터마이즈, 되돌리기 안전성 등 실제 손이 가는 부분을 반복적으로 다듬었습니다.
4. **재사용 가능한 구조** — 로직(core)과 UI를 분리해두었기에, KWI Creator를 standalone에서 Maya 내부 툴로 옮길 때 생성 로직을 그대로 재사용할 수 있었습니다.
