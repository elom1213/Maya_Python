## 2. 실측으로 확인한 것 ★

계획을 세우기 전에 mayapy 로 다섯 가지를 재 봤다. **셋이 설계를 바꿨다.**

### 2-1. `ikRPsolver` 는 **끝 조인트를 회전시키지 않는다** ★★

```
핸들을 옮긴 뒤
  j1(루트) rotate [0,0,0] -> [0,0,-17.198]   바뀜
  j2(중간) rotate [0,0,0] -> [0,0, 80.793]   바뀜
  j3(끝)   rotate [0,0,0] -> [0,0,  0.000]   그대로
```

**→ A2 는 `A[-1]` 의 회전을 정하지 못한다.** 즉 A2 가 정하는 것은

| A | 회전이 정해지는 조인트 | 안 정해지는 조인트 |
|---|---|---|
| 팔 L/R | `upperarm` · `lowerarm` | **`hand`** |
| 다리 L/R | `thigh` · `calf` | **`foot`** |

이것이 4장 겹침 분석의 뼈대다. **A3 의 `foot_r` 규칙은 중복이 아니라 필수**였다.

> **2·3차 갱신으로 구멍이 다 메워졌다.**
> **다리**는 `tail` 이 잡고(4-7), **팔**은 `preserve` — 즉 **마야 IK 가 하는 것과 똑같이
> 그대로 둔다**(2-6 · 4-9). 이제 A2 는 `A[-1]` 을 **어떻게 할지 항상 말한다.**

### 2-2. "IK 를 걸었을 때의 회전" 은 **그대로는 계산이 안 된다** ★★

RP 솔버는 체인을 **강체로 회전**시켜 (a) 끝이 핸들에 닿고 (b) 체인 평면이 폴을 지나게
할 뿐이다. **로컬 축 중 무엇이 폴을 향할지는 솔버가 아니라 조인트의 원래 방향이 정한다.**

실측(폴을 월드 +Z 에 두고):

```
k1  +X=[0.8, 0, 0.6]   +Y=[0.6, 0, -0.8]   +Z=[0, 1, 0]
```

체인 평면은 월드 XZ 평면인데 로컬 **+Z 는 평면의 법선**(월드 +Y)이 됐다 — 만들 때의
방향을 그대로 물려받은 것이다.

**→ "ikHandle 을 걸었을 때의 회전값" 은 시작 방향에 의존하므로, 방향을 *만들어 내는*
규칙으로는 그대로 못 쓴다.** 실제로 구현할 수 있는 동치 형태는 하나뿐이다:

> **forward(C) 축을 다음 조인트로 aim 하고, "up" 축을 폴 타깃 B 쪽으로 둔다.**

**어느 축이 up 인가**가 비어 있다 — 6-1 열린 질문. **A3 가 답을 준다**(4-3 참고).

### 2-3. 조인트를 "월드 회전 0,0,0" 으로 만드는 법

부모가 회전해 있는 자식 조인트에서:

| 방법 | 결과 |
|---|---|
| (a) `rotate = 0` | `[64.8, 33.7, 98.7]` — `jointOrient` 가 남는다 |
| (b) `rotate = 0` + `jointOrient = 0` | `[30, 40, 50]` — **부모 회전이 남는다** |
| (c) `xform -ws -ro 0 0 0` | `[0,0,0]` ✅ 단 값이 **`rotate` 로 들어간다** |
| (d) (c) 뒤 `rotate` 를 `jointOrient` 로 옮기고 `rotate = 0` | `[0,0,0]` ✅ **`rotate` 도 0** |

**→ (d) 를 쓴다.** 템플릿 조인트는 `rotate` 를 0 으로 두고 방향은 `jointOrient` 가 갖는
것이 리깅 관례고, 뒤에 오는 Match/Length 도 깨끗한 채널을 전제한다.

### 2-4. `mirrorJoint -mirrorYZ -mirrorBehavior` 가 만드는 것

```
원본  +X=[0.97, 0,  0.243]   위치 [ 2, 10, 0]
미러  +X=[0.97, 0, -0.243]   위치 [-2, 10, 0]
      +Y=[0, -1, 0]   +Z=[-0.243, 0, -0.97]      <- Y·Z 만 뒤집힌다
```

**forward(+X)는 월드에서 같은 쪽을 보고, +Y·+Z 만 뒤집힌다.** 그래서 오른쪽 조인트는
**자식이 −X 방향에 있는데 로컬 +X 는 +X 를 본다** → **오른팔의 forward 는 −X**.

**→ A2 의 `arm_r : −X` 와 정확히 맞물린다.** 팔은 Behavior 미러가 맞다.
반대로 **다리는 A3 가 forward 를 +X 라고 못박았다** — 즉 다리는 Behavior 미러가 **아니고**
**위치만 미러한 뒤 방향은 새로 만든다.**

### 2-5. 원하는 축 두 개로 방향을 직접 만들 수 있다

```
fwd=(0,1,0), hint=월드 +Z  ->  +X=[0,1,0]  +Y=[-1,0,0]  +Z=[0,0,1]
```

`side = hint × fwd`, `up = fwd × side` 로 정규직교 기저를 만들어 `xform -ws -m` 으로
넣으면 된다. **A1 · A2 · A3 의 모든 회전 규칙이 이 한 가지 계산으로 표현된다.**

### 2-6. "세팅 전과 똑같은 회전값" 은 **로컬**이다 ★

`hand_l/r` 규칙(`preserve`)에는 갈래가 하나 있다 — **로컬 값**을 지키는가, **월드 방향**을
지키는가. **둘은 동시에 만족할 수 없다.** 마야 IK 가 실제로 무엇을 하는지 재 봤다.

손목을 `jointOrient = [0,0,25]` 로 잡아 두고 핸들을 옮겼다:

| | `rotate` | `jointOrient` | **월드** |
|---|---|---|---|
| IK 걸기 전 | `[0,0,0]` | `[0,0,25]` | `25.0` |
| 핸들 이동 후 | `[0,0,0]` | `[0,0,25]` | **`91.02`** |

**→ 마야 IK 는 로컬(`rotate` + `jointOrient`)을 지키고, 월드 방향은 부모를 따라 움직인다.**
(참고: 월드를 되돌리려 하면 `rotate` 가 `[0,0,-66.02]` 로 바뀐다 — 로컬이 깨진다.)

**→ 설계 결정**: `preserve` = **로컬 값을 그대로 둔다.** 사용자의 말("ikHandle 세팅을 하기
전과 똑같은 회전값")과 마야 동작이 **둘 다 로컬을 가리킨다.**

> **결과를 감추지 않는다.** `upperarm`/`lowerarm` 이 회전하므로 **`hand` 의 월드 방향은
> 따라 움직인다.** 위 예에서 `25° → 91°` 다. 툴은 그 **변화량을 표에 적는다** — 손목이
> 크게 돌아갔다면 사용자가 즉시 안다.
> 월드를 지키는 쪽이 필요해지면 `preserve: "world"` 한 줄이면 된다(5-1).

### 2-7. 구현하며 드러난 것 두 가지 ★ (2026-08-28, 4차)

계획을 코드로 옮기면서 **계획에 없던 함정 두 개**가 나왔다. 둘 다 검증이 잡았다.

#### (1) 부모를 돌리면 **후손이 전부** 딸려 움직인다 — 직접 자식만 되돌리면 모자란다

척추를 위에서부터 정렬하니 오차가 **조인트마다 90도씩 누적**됐다:

```
pelvis   +X=[0,1,0]    OK
spine_01 +X=[-1,0,0]   90도 밀림
spine_02 +X=[0,-1,0]   180도 밀림
```

원인은 **다음 조인트의 aim 을 이미 끌려간 위치로 계산**한 것이었다.
처음에는 **직접 자식만** 제자리로 되돌리게 짰는데 그걸로 모자랐다 — 손자가 끌려간 채
남는다(실측: `c` 가 `(0,120,0)` → `(-10,110,0)`).

**→ 조인트를 돌릴 때마다 그 조인트의 *모든 후손* 위치를 되돌린다.** 되돌리는 순서는
**부모부터** — 부모를 나중에 옮기면 자식이 또 움직인다. 방향 단계 전체가 끝난 뒤에도
한 번 더 되돌려 안전망을 둔다.

#### (2) forward 를 정확히 맞추면 **up 은 그만큼 기운다** — 직교화의 필연

발의 규칙은 "`+Z` 가 월드 `+Y`" 인데, forward 도 다음 조인트를 봐야 한다.
**두 조건은 체인이 수평이 아닌 한 동시에 만족될 수 없다.**

```
foot -> ball 방향이 수직에서 36.87도 기울면
  forward(+X) 오차 = 0.00 도      <- 정확
  +Z 와 월드 +Y  = 36.87 도       <- 딱 그만큼 기운다
```

**→ forward 를 우선한다.** 본(bone)이 체인을 따라 서지 않으면 방향이 무의미하기 때문이다.
`+Z` 는 **월드 `+Y` 를 forward 에 직교화한 것**, 즉 가능한 한 `+Y` 에 가까운 값이 된다.

> **그 편차를 감추지 않는다.** tail 도 폴 체인처럼 **각도를 로그에 적는다** —
> `+Z is 36.87 deg off world +Y - that is how far the chain itself leans`.
> 실제 케이지의 발은 훨씬 평평하므로 이 값은 작아야 한다. **크면 배치가 이상한 것이다.**

## 4. A3 겹침 분석 — 무엇을 생략할 수 있나 ★

> 사용자 요청: *"A3 의 요청이 A2 때문에 저절로 세팅되는 부분이 있다면 그 부분은 생략해"*

### 4-1. 생략 가능 — **"오른쪽 다리의 forward 축은 +X"**

A2 의 `leg_r` 이 이미 `C = +X` 다. **완전히 같은 말이므로 A3 에서 뺀다.**

### 4-2. ~~생략 불가~~ → **2차 갱신으로 생략 가능** — `[foot_r, ball_r, ballEnd_r]`

**1차 판단**: 2-1 대로 IK 는 끝 조인트를 회전시키지 않으므로 A2 가 `foot_r` 을 손대지
못하고, `ball_r`·`ballEnd_r` 은 A2 목록에 없다 → **A3 가 정해야 한다.**

**2차 갱신(2026-08-28)**: 사용자가 **같은 규칙을 왼발에도 주면서 A2 에 넣자고** 했다.
그러면 A2 의 `leg_r` 항목이 **tail 로 이 셋을 직접 갖게 되므로** A3 의 이 항목은
**A2 와 완전히 같은 말이 된다 → 생략한다.** 판단 근거는 4-7.

### 4-3. **판단 필요** — `[thigh_r, calf_r]` 의 `+Z → 월드 +Z`

이 둘은 A2 가 회전을 정하는 조인트다. 그래서 **두 규칙이 같은 조인트에 두 개의 방향을
지정**하고 있다. 셋 중 하나다:

| 가능성 | 뜻 |
|---|---|
| (a) **같은 것** | 폴 타깃이 월드 +Z 쪽에 있어 A2 의 결과가 곧 `+Z→월드+Z` 다 → **생략** |
| (b) **A3 가 up 축을 알려 주는 것** | A2 의 빈칸(2-2 "어느 축이 up 인가")이 **+Z** 라는 뜻 → **생략하되 A2 에 반영** |
| (c) **서로 다른 것** | A2 의 폴 기준 롤과 A3 의 월드 기준 롤이 어긋난다 → **하나가 이겨야 한다** |

**(b) 로 읽는 것이 가장 앞뒤가 맞는다.** 2-2 에서 A2 는 "up 축이 무엇인가" 가 비어 있었고,
A3 가 다리에 대해 `+Z` 라고 말하고 있다. 폴 타깃은 무릎 앞에 놓이므로 `+Z` 가 폴을
향하는 축이라는 해석과 자연스럽게 이어진다.

**→ 설계 결정**: **up 축 = `+Z`, 폴 타깃 방향.** A3 의 `[thigh_r, calf_r]` 항목은 생략한다.

> **다만 조용히 믿지 않는다.** Orient 를 돌린 뒤 **`+Z` 와 월드 `+Z` 사이 각도를 재서
> 표에 적는다.** 폴 타깃이 예상과 다른 곳에 있으면 그 숫자가 바로 드러난다 —
> 가정이 틀렸을 때 **리그가 조용히 틀리는 대신 화면에 뜬다.**
> 이 검산이 (a)/(b) 와 (c) 를 실제 케이지에서 갈라 준다.

### 4-4. 생략 불가 — **위치 미러 전체**

A2 는 **아무것도 옮기지 않는다**(회전만 정한다). 오른쪽 다리·팔의 **위치**와 위치 전용
14개는 전부 A3 의 몫이다.

### 4-5. 생략 불가 — `helper_clavicle_r`

A1 · A2 어디에도 없다. A3 의 Behavior 미러가 유일한 규칙이다.

### 4-6. ★ 순서가 강제된다 — **미러가 A2 보다 먼저**

A2 의 오른쪽 두 벌은 **`polTgt_arm_r` · `polTgt_leg_r` 를 읽는다.** 그런데 그 폴 타깃을
제자리에 놓는 것은 **A3 의 위치 미러**다.

```
A3(위치 미러)  ->  A1(척추)  ->  A2(팔·다리 회전 + tail)  ->  A3(clavicle_r 방향)
```

**A3 가 앞뒤로 두 번 나뉜다.** 순서를 지키지 않으면 오른쪽 팔·다리가 **옛 폴 위치로**
계산되어 조용히 틀린다.

> **2차 갱신 뒤 마지막 칸이 가벼워졌다** — 발 회전이 A2 의 tail 로 들어가서
> 뒤쪽 A3 에는 **`clavicle_r` 하나**만 남는다(4-8).

### 4-7. **판단: `tail` 을 A2 에 넣는 것이 맞다** ★

사용자 제안: `[foot_l, ball_l, ballEnd_l]` 의 `+Z` 를 월드 `+Y` 로. **A2 절차에 넣자.**

**넣는 것이 맞다. 이유가 사용자가 든 것보다 하나 더 있다.**

**(1) A2 의 구멍을 A2 안에서 메운다** — 2-1 에서 드러난 "IK 는 `A[-1]` 을 회전시키지
않는다" 는 **다리만의 문제가 아니라 A2 라는 규칙의 구조적 구멍**이다. 구멍을 규칙 밖
목록으로 때우면, A2 를 읽는 사람은 **끝 조인트가 어디서 정해지는지 알 수 없다.**
tail 을 A2 항목 안에 두면 `chain + pole + forward + tail` 로 **한 항목이 그 부위의 방향을
전부 설명한다.**

**(2) ★ 같은 조인트를 두 규칙이 이름 부르는 상태가 사라진다** — 이게 더 큰 이득이다.
지금 구조에서는 `foot_r` 이 **A2 의 체인 끝**이자 **A3 의 월드축 그룹**에 동시에 들어 있다.
"A2 는 끝 조인트를 안 건드리니까 충돌이 아니다" 는 **실측으로만 아는 사실**이고 json 에는
안 적혀 있다. 나중에 A2 구현이 조금만 달라져도(예: 끝 조인트도 정렬하게) **두 규칙이
말없이 싸운다.** tail 로 합치면 **`foot_r` 을 부르는 곳이 하나**가 된다.

**(3) 좌우가 대칭이 된다** — 지금은 오른발만 규칙이 있어 A3(미러 규칙) 안에 회전 규칙이
섞여 있었다. 양쪽에 같은 tail 을 주면 **A3 는 순수하게 "미러" 만 남는다**(4-8).

**치르는 값** — A2 한 항목이 up 기준을 **둘** 갖게 된다(IK 부분은 폴, tail 은 월드 축).
그만큼 스키마가 복잡해진다. **그래도 낼 값어치가 있다** — (2) 의 모호함이 더 비싸다.

**대안과 비교했다**: "목록은 그대로 두고, **A2 의 모든 끝 조인트가 다른 그룹에 정확히
한 번 나오는지 툴이 검사**한다" 도 가능하다. 하지만 그건 *잊으면 경고*고, tail 은
*잊을 수 없는* 구조다. **잊을 수 없는 쪽이 낫다.**

**효과 (실측 집계)**

| | 회전 규칙 있는 조인트 | 규칙 없는 조인트 | 왼발 |
|---|---|---|---|
| 제안 전 | 35 | 45 | ❌ 미해결 |
| **제안 후** | **38** | **42** | ✅ 해결 |

### 4-9. `preserve` 는 **빈칸이 아니라 결정이다**

`hand_l/r` 은 2차 갱신까지 "규칙 없음" 이었고, 4-7 에서 **"다리에 tail 을 준 지금 팔만
비어 있는 것이 눈에 띈다"** 고 적어 뒀다. 3차 갱신에서 사용자가 답했다 —
**tail 을 주는 게 아니라, 손대지 않는 것이 규칙이다.**

이 둘은 **씬에 대한 결과가 같지만 뜻이 다르다**:

| | 씬 | 뜻 | UI 표시 |
|---|---|---|---|
| `preserve` | 안 바뀐다 | **정했다** — IK 가 하는 것과 같다(2-6) | `preserved` |
| 규칙 없음 | 안 바뀐다 | **아직 안 정했다** — 확인이 필요하다 | `no rule` |

**둘을 같은 칸에 담으면, 확인해야 할 빈칸이 결정된 항목에 묻힌다.** 그래서 json 에
`"tail": "preserve"` 로 **명시적으로 적고**, 표에서도 갈라 보여 준다.

### 4-8. A3 가 남기는 것 — **순수한 미러만**

2차 갱신 뒤 A3 에는 회전 규칙이 **`clavicle_r` 하나**만 남는다. 나머지는 전부 위치다.
규칙의 성격이 깨끗하게 갈렸다:

| 규칙 | 성격 |
|---|---|
| A1 | 척추 — 월드 기준 방향 |
| A2 | 팔·다리 — 체인 방향(IK 부분은 폴, tail 은 월드 축) |
| A3 | **미러** — 위치 + `clavicle_r` 방향 |

### 겹침 분석 요약

| A3 항목 | 판정 |
|---|---|
| 오른쪽 다리 forward = +X | ❌ **생략** (A2 의 C 와 동일) |
| `[thigh_r, calf_r]` +Z → 월드 +Z | ❌ **생략** (A2 의 up 축 정의로 흡수, **각도 검산으로 확인**) |
| `[foot_r, ball_r, ballEnd_r]` +Z → 월드 +Y | ❌ **생략** — **2차 갱신으로 A2 의 tail 이 됐다**(4-2 · 4-7) |
| `clavicle_r` Behavior 미러 | ✅ 필요 — **A3 에 남는 유일한 회전 규칙** |
| 오른쪽 팔·다리 **위치** 미러 | ✅ 필요 |
| 위치 전용 14개 (+ 회전 0) | ✅ 필요 · **A2 보다 먼저** |

## 5. 설계

### 5-1. 규칙은 **json**, 코드는 세 가지 계산만 안다

`app/data/mapping/<version>/orient_map.json` 신규. 코드에 조인트 이름을 박지 않는다.

```jsonc
{
  "world_zero_default": true,          // A1 체크박스 기본값

  "aim_groups": [                      // A1
    {
      "name": "spine",
      "joints": ["helper_pelvis", "...", "helper_head"],
      "forward": "+X",
      "up": "+Z", "up_target": "world", "up_world": "+Z",
      "world_zero_option": true        // 체크박스가 이 그룹을 덮는다
    }
  ],

  "pole_chains": [                     // A2
    { "name": "arm_l",
      "joints": ["helper_upperarm_l", "helper_lowerarm_l", "helper_hand_l"],
      "pole": "helper_polTgt_arm_l",
      "forward": "+X", "up": "+Z",
      "expect_up_world": "+Z",         // 4-3 의 검산값 (틀리면 표에 각도가 뜬다)
      // ★ 팔의 끝 조인트(hand)는 **일부러 건드리지 않는다** - 마야 IK 와 같다(2-6).
      //   null 이 아니라 "preserve" 라고 적는다 - "아직 안 정함" 과 구분해야 한다(4-9).
      //   월드 방향을 지키고 싶으면 "preserve_world" 로 바꾼다.
      "tail": "preserve"
    },
    { "name": "leg_l",
      "joints": ["helper_thigh_l", "helper_calf_l", "helper_foot_l"],
      "pole": "helper_polTgt_leg_l",
      "forward": "+X", "up": "+Z",
      "expect_up_world": "+Z",
      // ★ IK 가 끝 조인트를 안 돌리므로(2-1) 끝 조인트부터는 tail 이 잡는다.
      //   joints[-1] 로 시작해야 한다 - 로드할 때 검사한다.
      "tail": { "joints": ["helper_foot_l", "helper_ball_l", "helper_ballEnd_l"],
                "forward": "+X", "up": "+Z", "up_world": "+Y" }
    }
  ],

  "mirror": {                          // A3
    "plane": "YZ",
    "behavior": [                      // 방향까지 미러 (팔)
      { "source": "helper_clavicle_l", "target": "helper_clavicle_r",
        "children": true }
    ],
    "position_only": [                 // 위치만 + 월드 회전 0
      "helper_polTgt_arm_l", "helper_polTgt_arm_r", "..." ],
    "position_then_orient": [          // 위치만 미러하고 방향은 뒤에서 만든다 (다리)
      { "source": "helper_thigh_l", "target": "helper_thigh_r", "children": true } ]
  },

  // world_axis_groups 는 2차 갱신에서 없앴다 - 유일한 사용처였던 발이
  // A2 의 tail 로 들어갔다(4-7). 필요해지면 그때 되살린다.
}
```

코드가 아는 계산은 **셋뿐**이다:

| 계산 | 하는 일 |
|---|---|
| `orient_aim(joint, child, forward, up, up_hint)` | 2-5 의 기저 계산. **A1 · A2 의 IK 부분 · A2 의 tail 이 전부 이 하나를 쓴다** (`up_hint` 만 폴 위치 / 월드 축으로 달라진다) |
| `world_zero(joint)` | 2-3 의 (d) |
| `mirror_transform(src, dst, plane, behavior)` | 2-4 |

### 5-2. `mirrorJoint` 를 **그대로 쓰지 않는다**

`cmds.mirrorJoint` 는 **조인트를 새로 만든다.** 그런데 오른쪽 조인트는
`Create Template Joints` 가 이미 만들어 뒀다 — 또 만들면 이름이 갈린다.

→ **임시로 미러본을 만들어 트랜스폼만 베껴 넣고 지운다.** 마야의 Behavior 계산을
직접 구현하지 않고 빌려 쓰되(2-4 로 동작을 확인했다), 씬에는 남기지 않는다.
전체가 `undo_chunk()` 안에서 돈다.

### 5-3. 방향은 `jointOrient` 에 넣고 `rotate` 는 0 으로

2-3 (d). 모든 규칙이 끝난 뒤 **`rotate` 가 전부 0 인지 검사**해서 아니면 알린다.

### 5-4. 체인의 **마지막 조인트**는 앞 조인트의 방향을 물려받는다

A1 의 `helper_head` 는 자식이 없어 aim 할 대상이 없다(실측: `children=[]`).
`helper_neck_02` 의 방향을 그대로 받는 것이 리깅 관례다. **A1 체크박스가 켜져 있으면
어차피 월드 0 이라 이 문제가 안 생긴다**(기본 켬).

### 5-5. UI — `Orient` 단계 탭

`STEPS` 표에 줄 하나. Match · Length 와 같은 **`plan()` / `apply()` 분리**:

```
┌ Match │ Length │ Orient ─────────────────────────────────┐
│ [x] Spine joints: world zero (uncheck to aim +X / +Z)    │  ← A1 체크박스
│ [x] Mirror left to right before orienting                │  ← 4-6 순서
│ ┌────────────┬──────────┬─────────┬────────────────────┐ │
│ │ Joint      │ Rule     │ Up dev  │ Status             │ │
│ │ spine_01   │ A1 world │ -       │ ok                 │ │
│ │ thigh_r    │ A2 pole  │ 0.4 deg │ ok                 │ │  ← 4-3 검산
│ │ foot_r     │ A2 tail  │ -       │ ok                 │ │
│ │ hand_l     │ A2 keep  │ 66.0 deg│ preserved          │ │  ← 4-9 · 월드 변화량
│ │ thumb_01_l │ (none)   │ -       │ no rule - untouched│ │  ← 3장의 빈칸
│ └────────────┴──────────┴─────────┴────────────────────┘ │
│ [ Check ]                                  [ Orient ]    │
└──────────────────────────────────────────────────────────┘
```

- **`Check`** — 계산만 하고 **씬을 안 바꾼다**. `Up dev` 열이 4-3 의 검산값이다.
- **`Orient`** — 실제로 적용. **undo 한 스텝.**
- **`preserved` 와 `no rule` 을 갈라 보여 준다**(4-9). 규칙 없는 **40개**는
  `no rule - untouched`, 일부러 안 건드리는 `hand_l/r` 은 `preserved`.
  **조용히 빠뜨리지도, 결정된 것을 빈칸처럼 보이게도 하지 않는다.**
- **`preserve` 행의 `Up dev` 열에는 월드 방향이 얼마나 따라 움직였는지**를 적는다(2-6).
  로컬은 그대로여도 **부모가 돌면 손목은 돌아간다** — 그 양을 감추지 않는다.

### 5-6. 다른 단계와의 관계

- **Match 보다 먼저**여야 한다 — Match 는 케이지 컨트롤러를 조인트 자리로 옮기므로,
  방향이 정해진 뒤에 돌아야 한다.
- **Length 와는 무관**하다 — 길이는 위치만 쓴다.
- **IK 세션은 필요 없다** — 템플릿 조인트에는 ikHandle 이 안 걸려 있다
  (`D01_IK_handle` 은 케이지 쪽이다). 다만 **Orient 도 조인트를 회전시키므로**,
  나중에 템플릿에 IK 가 붙는다면 그때 같은 세션을 두른다.
