# A00390_WindTool_V02 재생 속도 — `windPhaseTime` 표현식이 범인이다

체인(= 드라이버) 30개를 넘기면 재생이 30fps 아래로 떨어지는 문제의 원인을 찾고, 고치는 방법을
정한다.

- **작성일**: 2026-08-24
- **대상**: `tools/A00390_WindTool_V02/app/core/wind_manager.py` — `_make_phase_expression()`
  (세 탭이 **공유**한다: Sine · Chain Wave · Chain Wave Lite)
- **상태**: **진단 완료 · 미적용** (이 문서는 계획서다. 코드는 아직 손대지 않았다)
- **측정 환경**: `mayapy` (Maya 2024) 헤드리스 · Parallel EM · 체인당 조인트 5 · 프레임 80–100 평균

> [!important] 한 줄 요약
> 느린 것은 **노드망이 아니라 드라이버마다 붙는 `expression` 노드 1개**다. 그 표현식이 매
> 프레임 `getAttr -time` 을 **시작 프레임부터 현재 프레임까지 반복 호출**한다. 표현식을 노드
> 3개로 바꾸면 30체인 기준 **58.7ms → 0.64ms (약 92배)** 다. 상수 속도에서 결과 회전값은
> **완전히 동일**하다(오차 0.000e+00).

## 1. 증상 재현 — 보고와 수치가 일치한다

체인 수를 늘려 가며 프레임을 이동시키고 1프레임 평가 시간을 쟀다.

| 체인 수 | 씬 전체 노드 | ms / frame | fps | 보고된 증상 |
|--------:|-------------:|-----------:|----:|-------------|
| 1 | 126 | 1.76 | 567 | |
| 5 | 422 | 9.48 | 106 | |
| 10 | 792 | 19.25 | 52 | |
| **20** | 1,532 | 39.03 | **26** | "20개면 30fps 는 보장" |
| **30** | 2,272 | 58.26 | **17** | "30개 이상이면 30fps 안 나옴" |
| **50** | 3,752 | 99.20 | **10** | "50개 이상이면 15fps" |

헤드리스라 **뷰포트 그리기 비용이 빠진 값**인데도 이렇다. 즉 병목은 그리기가 아니라 **DG 평가**다.

### 결정적 단서 — 재생할수록 느려진다

같은 씬(30체인)에서 **어느 구간을 재생하느냐**에 따라 비용이 달라진다.

| 재생 구간 | ms / frame |
|-----------|-----------:|
| 1 – 20 | 11.07 |
| 50 – 70 | 38.83 |
| 100 – 120 | 70.33 |
| 180 – 200 | **114.23** |

프레임 번호에 **정비례**한다. 노드 개수는 그대로인데 시간만 늘어난다면, 원인은 노드망이 아니라
**"프레임 번호만큼 일을 더 하는 무언가"** 다.

## 2. 원인 — `getAttr -time` 을 매 프레임 O(frame)번 부른다

`wind_manager._make_phase_expression()` 이 드라이버마다 만드는 표현식이다.

```mel
float $cf = frame;
int $start = 1;
int $fend = (int)floor($cf);
float $acc = 0.0;
float $prev = `getAttr -time $start DRIVER.windSpeed`;
int $f;
for ($f = $start + 1; $f <= $fend; $f++) {
  float $s = `getAttr -time $f DRIVER.windSpeed`;   // <-- 여기
  $acc += 0.5 * ($prev + $s);
  $prev = $s;
}
...
DRIVER.windPhaseTime = $start + $acc;
```

`windSpeed` 를 **시작 프레임부터 현재 프레임까지 사다리꼴 적분**한다. 의도는 옳다 — 속도에 키를
걸어도 위상이 역행하지 않게 하려는 것이다. 문제는 **비용**이다.

- 프레임 100 을 그리려면 드라이버 **하나가** `getAttr -time` 을 **99번** 부른다.
- 드라이버 30개면 한 프레임에 **약 3,000번**.
- `getAttr -time` 은 단순한 값 읽기가 아니라 **DG 를 그 시각으로 평가**하는 호출이다.
  표현식 평가 도중에 이걸 부르면 DG 재진입이 일어난다.
- `alwaysEvaluate=True` 라 매 프레임 무조건 다시 돈다.

### 원인 분리 실측 (30체인, 프레임 80–100)

| 상태 | ms / frame | fps |
|------|-----------:|----:|
| 현행 그대로 | **58.72** | 17 |
| expression 만 `nodeState=1` (HasNoEffect) | 3.57 | 280 |
| expression 만 **삭제** | **0.10** | 10,500 |
| expression 삭제 + 디버그 커브도 없음 | 0.05 | 20,907 |
| expression 있음 + 디버그 커브 없음 | 55.91 | 18 |

**재생 비용의 99.8% 가 expression 노드다.** 사인 LUT · 곱셈 · 쿼터니언 등 나머지 노드망은
전부 합쳐 0.05 ms — 사실상 공짜다. 디버그 커브도 DG 상으로는 무관하다(58.72 vs 55.91).

### 루프가 문제인가, `getAttr -time` 이 문제인가

표현식 개수는 그대로 두고 내용만 바꿔 봤다.

| 표현식 내용 | ms / frame |
|-------------|-----------:|
| 현행 (적분 루프 + `getAttr -time`) | **58.82** |
| O(frame) 루프는 그대로, `getAttr -time` 만 뺌 | **0.72** |
| O(1) 한 줄 (`phase = 1 + speed * (frame - 1)`) | 0.64 |

**MEL 루프 자체는 싸다. 범인은 `getAttr -time` 하나다.** 표현식 노드를 쓴다는 사실이 문제가
아니라, 표현식 안에서 시간을 옮겨 가며 DG 를 다시 평가한다는 점이 문제다.

### 비용은 체인 **개수**에만 붙는다 (조인트 수와 무관)

| 체인당 조인트 | 씬 노드 | ms / frame |
|--------------:|--------:|-----------:|
| 3 | 1,492 | 62.13 |
| 5 | 2,272 | 63.96 |
| 7 | 3,052 | 67.03 |
| 12 | 5,002 | 65.00 |

노드가 3.4배로 늘어도 시간은 그대로다. 반면 체인 수에는 정확히 비례한다.

| 체인 수 | expression | ms / frame |
|--------:|-----------:|-----------:|
| 10 | 10 | 22.33 |
| 20 | 20 | 44.79 |
| 30 | 30 | 60.94 |
| 40 | 40 | 84.05 |
| 50 | 50 | 103.80 |

드라이버 하나에 expression 하나이므로, **비용 = 체인 수 × 프레임 번호**다. 보고에서 "각 노드는
3~7개짜리 본 체인에 영향을 준다"고 한 것과 정확히 맞아떨어진다 — 조인트 수는 상관이 없었다.

## 3. 관측된 두 가지가 왜 그런지

### 3-1. Evaluation mode 를 바꿔도 똑같은 이유

| | DG(off) | Serial | Parallel |
|---|--------:|-------:|---------:|
| 현행 | 46.53 | 67.19 | 60.54 |
| 노드 경로로 고친 뒤 | 0.00 | 3.18 | **0.38** |

표현식이 평가 도중 `getAttr -time` 으로 DG 를 재진입하면 **EM 이 병렬화할 수 없는 작업**이 된다.
어느 모드를 골라도 이 일은 그대로 남는다. 고친 뒤에는 Parallel 이 Serial 보다 8배 빨라져 —
**EM 이 그제서야 제 일을 한다.**

### 3-2. `windEnvelope = 0` 이 아무 도움이 안 되는 이유

30체인에서 모든 드라이버의 `windEnvelope` 를 0 으로:

| | ms / frame |
|---|-----------:|
| `windEnvelope = 1.0` | 62.97 |
| `windEnvelope = 0.0` | **63.18** |

`windEnvelope` 는 **스윙 각도에 곱해지는 값**일 뿐이다. Maya DG 는 "이 값이 0이니 위쪽 계산을
건너뛰자" 를 하지 않는다 — 곱셈 노드가 결과를 내려면 두 입력이 다 필요하고, 그러려면
`windPhaseTime` 이 필요하고, 그러면 표현식이 돈다. **값을 0으로 만드는 것과 평가를 막는 것은
전혀 다른 일이다.** 보고하신 관측이 정확하다.

## 4. 해법 A (권장) — 표현식을 노드 3개로 바꾼다

상수 속도에서 위 표현식이 계산하는 값은 결국 이것이다.

```
acc   = Σ 0.5*(s + s)  =  s * (frame - start)          (s 가 상수이므로)
phase = start + s * (frame - start)
```

**즉 상수 속도의 적분은 곱셈 한 번이다.** 노드로 그대로 옮길 수 있다.

```
time1.outTime ──> addDoubleLinear(input2 = -start) ──┐
                                                     ├─> multDoubleLinear ──> addDoubleLinear ──> driver.windPhaseTime
                          driver.windSpeed ──────────┘        (× speed)         (+ start)
```

드라이버당 노드 **3개**, 표현식 **0개**.

### 값이 같은가 — 같다

상수 속도에서 현행 표현식과 노드 경로의 결과를 비교했다(끝 조인트 `rotateZ`, 프레임 1/7/33/100/250).

| windSpeed | max \|phase 차\| | max \|rotateZ 차\| | |
|----------:|----------------:|------------------:|---|
| +1.00 | 0.000e+00 | 0.000e+00 | 동일 |
| +2.50 | 0.000e+00 | 0.000e+00 | 동일 |
| −0.70 | 3.695e-13 | 0.000e+00 | 동일 |

**기존 씬의 룩이 변하지 않는다.** 이게 이 해법의 가장 큰 장점이다.

`time1.outTime` 은 `addDoubleLinear` 에 연결할 때 `unitConversion` 이 끼지 않고 **프레임 번호가
그대로** 나온다(film 24 / ntsc 30 / pal 25 / game 15 전부 37프레임에서 37.000 확인). 표현식의
`frame` 변수와 의미가 같다.

### 성능

| 체인 수 | 씬 노드 | 현행 | 해법 A |
|--------:|--------:|-----:|-------:|
| 30 | 2,272 | 59.32 ms (17 fps) | **0.64 ms (1,554 fps)** |
| 50 | 3,752 | 100.22 ms (10 fps) | **0.96 ms (1,043 fps)** |
| 100 | 7,452 | 205.19 ms (5 fps) | **1.84 ms (544 fps)** |
| 200 | 14,852 | 422.74 ms (2 fps) | **4.09 ms (244 fps)** |

그리고 **프레임 위치에 따른 증가가 사라진다**(구간 1–20 / 150–170 / 280–300 에서 0.400 / 0.396 /
0.381 ms — 평평하다).

목표였던 "50체인 30fps" 는 **여유롭게 넘긴다.** 헤드리스 측정이라 실제로는 뷰포트 그리기가
더해지지만, DG 평가가 0.96 ms 로 내려가면 남는 것은 그리기 비용뿐이고 그건 이 툴이 만드는
노드망과 무관하다(→ 7절).

### 잃는 것 — `windSpeed` 에 **키를 걸었을 때**의 적분

속도가 상수가 아니면 곱셈은 적분이 아니다. `windSpeed` 를 1프레임 0 → 100프레임 4 로 키잉하면:

| frame | 1 | 25 | 50 | 100 |
|-------|--:|---:|---:|----:|
| 현행 표현식 (적분) | 1.00 | 5.96 | 37.14 | 199.00 |
| 노드 경로 (곱셈) | 1.00 | 15.19 | 97.52 | 397.00 |

이 기능은 지금 문서화된 동작이므로(`_make_phase_expression` 독스트링: "가변 속도에서도 위상이
단조 전진") **버리지 않고 4-1 로 살린다.**

### 4-1. 가변 속도 보존 — 적분을 파이썬에서 미리 굽는다

`windSpeed` 에 키가 걸린 드라이버만, **같은 사다리꼴 적분을 파이썬에서 계산해
`windPhaseTime` 에 animCurve 로 굽는다.** 표현식은 여전히 0개다.

검증 (속도를 1→60→120 프레임에 0 / 4 / −2 로 키잉):

| frame | 1 | 15 | 30 | 60 | 90 | 120 | 150 |
|-------|--:|---:|---:|---:|---:|----:|----:|
| 현행 표현식 | 1.000 | 3.785 | 22.146 | 119.000 | 205.238 | 179.000 | 119.000 |
| 구운 커브 | 1.000 | 3.785 | 22.146 | 119.000 | 205.238 | 179.000 | 119.000 |

**max diff = 0.000e+00.** 값이 완전히 같다.

대가는 **라이브성**이다. 지금은 `windSpeed` 키를 고치면 즉시 반영되지만, 구운 뒤에는 다시 구워야
한다. 그래서 UI 에 **`Rebuild Phase`** 버튼을 둔다(선택한/모든 드라이버의 속도 커브를 다시 적분).

> 이 트레이드가 타당한 이유: 상수 속도(기본값이자 대부분의 사용)는 **아무것도 잃지 않고** 92배
> 빨라진다. 가변 속도는 원래도 드물고, 잃는 것은 "버튼 없이 즉시" 뿐이며 값은 동일하다.

### 4-2. 굽지 않고 **라이브를 유지하는** 방법이 있는가 — 있다 (추가 조사)

4-1 은 라이브성을 포기한다. "키를 걸어도 라이브를 유지할 수 있는가" 를 따로 파고들어
**세 가지 길**을 찾았고 전부 실측했다. 먼저 왜 어려운지부터.

> [!note] 본질적 제약
> DG 노드는 **현재 시각의 입력만** 본다. 누적 적분은 **과거 전체**에 의존한다. 그래서
> 순수 노드망으로는 적분을 만들 수 없다 — 상태를 가지면 랜덤 액세스 재생이 깨진다.
> 라이브로 적분하려면 셋 중 하나다: (a) 과거를 매번 다시 읽거나(현행, 느림),
> (b) 결과를 데이터로 미리 갖거나(4-1, 라이브 아님), (c) **커브 데이터에서 해석적으로 계산**한다.
> (c) 가 유일하게 라이브 + 빠름을 동시에 만족한다.

#### 방법 1 — 표현식을 **하나로 합치고**, 커브 데이터를 직접 적분 (권장)

`getAttr -time` 으로 과거를 **재평가**하는 대신, `keyframe -q -timeChange / -valueChange` 로
**키 데이터를 읽어** 구간별로 적분한다. 커브 조회는 DG 평가가 아니라서 싸고, 비용이 키 개수에만
붙어 **프레임 번호와 무관**하다.

여기서 결정적인 것이 하나 더 있다 — **표현식 노드의 개수 자체가 오버헤드다.**

| 30체인, 전부 `windSpeed` 에 키가 걸린 최악의 경우 | ms / frame |
|---|---:|
| 현행 (`getAttr -time`) | 63.49 |
| 커브 데이터 적분, **표현식 30개** (드라이버마다) | 5.84 |
| 커브 데이터 적분, **표현식 1개로 통합** | **1.38** |
| 참고: 계산이 아예 없는 빈 표현식 30개 | 0.65 |

계산을 하지 않는 표현식 30개만으로 0.65 ms 다. **표현식은 개수를 줄이는 것이 내용을 줄이는 것보다
중요하다.** 빌드 하나가 표현식 하나를 만들어 그 빌드의 드라이버 전부를 담당하게 한다.

- **라이브 100%** — 키를 고치면 즉시 반영됨을 확인(phase 199.000 → 648.333).
- **프레임 무관** — 구간 1–20 / 150–170 / 280–300 에서 5.89 / 5.69 / 5.82 ms (표현식 30개 기준).
- 스케일 (통합 표현식, 전부 키 걸린 최악): 30체인 1.35 ms(742 fps) · 50체인 2.77 ms(362 fps) ·
  100체인 5.00 ms(200 fps) · 200체인 10.18 ms(98 fps).

**대가 — spline 탄젠트에서 값이 달라진다.**

| 탄젠트 | 현행 대비 max 차이 |
|---|---|
| `linear` | **0.000** (완전 일치) |
| `spline` (기본값) | 49.486 (최대값의 **21%**) |

현행은 **프레임 단위 사다리꼴**, 이 방법은 **키 구간 선형**이라 키 사이의 곡률을 놓친다.
표현식 안에서 커브를 프레임 단위로 평가할 방법을 찾아봤지만 **없다**:

- `keyframe -q -eval -t` 의 `-t` 는 **TimeRange 타입 리터럴**이라 루프 변수를 받지 못한다.
  MEL 스코프·표현식 양쪽에서 문법 4종(`-t $f`, `-t "30:30"`, `-t 30`, `eval()` 동적 생성)
  **전부 실패**했다. Python `cmds.keyframe(..., eval=True)` 로는 되지만 표현식은 MEL 전용이다.
- 남는 것은 `getAttr -time` 뿐인데 그게 바로 원흉이다.

탄젠트까지 읽어 **3차 에르미트로 적분**하면 곡률을 반영할 수 있다(`keyTangent -q -ix -iy -ox -oy`).
다만 그러면 현행보다 **더 정확해질 뿐 같아지지는 않는다** — 현행 자체가 프레임 샘플 근사다.
시제 구현은 부분 구간에서 값이 어긋나 아직 **검증되지 않았다**(정확한 공식은 추가 작업 필요).

#### 방법 2 — 커브 변경을 감지해 **자동으로 다시 굽기**

4-1 의 굽기를 유지하되, `windSpeed` 커브가 바뀔 때 **자동으로** 다시 굽는다. 값이 현행과
**100% 동일**하고 재생 비용도 최소(30체인 0.78 ms)라 가장 매력적으로 보이지만, 함정이 있다.

| 콜백 | 재생 60프레임 중 발동 횟수 |
|---|---:|
| `MNodeMessage.addNodeDirtyCallback` | **315** ← 재생마다 발동, 그대로 쓰면 재앙 |
| `MNodeMessage.addAttributeChangedCallback` | **305** ← 마찬가지 |
| `MAnimMessage.addAnimKeyframeEditedCallback` | **0** ← 이상적 |

`addAnimKeyframeEditedCallback` 이 재생에 반응하지 않아 정답처럼 보이지만, 헤드리스에서는
`cmds.keyframe` / `setKeyframe` / `cutKey` 편집에도 **발동하지 않았다**(0회). 반면 dirty 콜백은
편집에 1~4회 발동한다. 즉 **실제 UI 에서 그래프 에디터 조작에만 반응하는지 재확인이 필요**하다.

dirty 콜백을 쓰려면 **debounce** 가 필요하다 — 콜백에서는 플래그만 세우고, idle 시점에 키
데이터가 실제로 바뀐 경우에만 다시 굽는다. 재생 중에는 idle 이 오지 않아 재굽기가 돌지 않는다.
구현은 가능하지만 헤드리스로 완전히 검증할 수 없다(UI 이벤트 루프가 필요).

콜백은 **씬에 저장되지 않는다.** 툴을 다시 열 때 씬의 드라이버를 스캔해 재등록해야 한다.
다만 콜백이 없어도 **구운 값은 그대로 남아** 안전하게 열화한다(수동 `Rebuild Phase` 로 갱신).

#### 방법 3 — `windPhaseTime` 을 **직접** 키잉한다

적분을 없애고 애니메이터가 위상 커브를 직접 편집한다. **완전 라이브 · 비용 0**
(30체인 0.78 ms · 200체인 3.91 ms). 그래프 에디터에서 **커브의 기울기가 곧 속도**라
개념적으로 잃는 것도 없다 — "속도로 그리고 싶다" 는 Speed→Phase 변환 버튼으로 받는다.
다만 UI 상의 개념이 바뀌므로 사용자 판단이 필요하다.

#### 정리

| | 라이브 | 30체인 | 현행과 값 | 결정적 약점 |
|---|---|---:|---|---|
| 4-1 굽기 + 수동 버튼 | ✗ (버튼) | 0.64 ms | **동일** | 키 고칠 때마다 버튼 |
| **방법 1 통합 표현식** | **✓ 진짜 DG 라이브** | 1.35 ms | spline 21% 차이 | 값이 달라짐 |
| 방법 2 콜백 자동 재굽기 | ✓ 체감 라이브 | 0.78 ms | **동일** | debounce 필요 · 씬 저장 안 됨 |
| 방법 3 phase 직접 키잉 | ✓ 완전 | 0.78 ms | 해당 없음 | 개념 변경 |

**권장: 방법 1.** 유일하게 진짜 라이브이면서 구현이 단순하고(표현식 1개), 목표 규모에서
충분히 빠르다. 상수 속도 드라이버는 4절의 노드 경로로 두는 **하이브리드**면 더 낫다 —
30체인 중 키 걸린 것이 2개면 **1.11 ms(903 fps)**, 5개면 1.55 ms, 10개면 2.49 ms 다.

값이 달라지는 것이 받아들여지지 않는다면 **방법 2**, 개념 변경이 괜찮다면 **방법 3** 이다.

## 5. 해법 B (요청하신 방식) — `[0,1]` 어트리뷰트로 체인 끄기

> **요청 내용**: 드라이버에 `[0,1]` 실수 어트리뷰트를 두고, 0 이면 그 체인에 연결된 노드의 평가를
> 통째로 중단시킨다. 보고 싶은 체인 한두 개만 켜고 나머지는 다 꺼서 30fps 를 확보한다.

### 5-1. 되는가 — 된다. 단, 어트리뷰트 값으로는 안 되고 `nodeState` 로 해야 한다

Maya 에서 **"값이 0이니 계산을 건너뛴다"는 일은 일어나지 않는다**(3-2 에서 실측). 평가를 실제로
멈추려면 노드의 `nodeState` 어트리뷰트를 써야 한다.

| `nodeState` | 뜻 |
|---|---|
| 0 `Normal` | 정상 평가 |
| 1 `HasNoEffect` | 계산을 건너뛰고 입력을 그대로 통과 |
| 2 `Blocking` | 출력을 마지막 값으로 고정 |

현행 셋업(30체인)에서 **2개만 남기고 28체인의 expression 을** 끈 결과:

| 상태 | ms / frame | fps |
|------|-----------:|----:|
| 전부 켜짐 | 57.67 | 17 |
| 28개 `nodeState=1` | 7.23 | 138 |
| 28개 `nodeState=2` | 7.15 | 140 |
| 28개 **삭제** (상한) | 3.85 | 260 |

**8배 빨라진다. 요청하신 방식은 실제로 동작한다.**

### 5-2. 그런데 해법 A 를 하면 이 방식이 필요 없어진다

해법 A 적용 **후** 200체인에서 같은 실험:

| 상태 | ms / frame | fps |
|------|-----------:|----:|
| 200체인 전부 켜짐 | 4.28 | 395 |
| 198체인 mute (노드 12,080개) | 2.29 | 436 |

노드망이 이미 공짜라 **끄나 마나 2배 이내**다. 반면 해법 A 는 **92배**다.

> [!warning] 두 해법은 대안이 아니다
> 해법 B 만 하면 17 fps → 138 fps 이지만, **살아 있는 체인의 expression 이 여전히 O(frame)** 이라
> 긴 구간을 재생할수록 다시 느려진다(30체인 기준 프레임 180에서 114 ms). 근본 원인이 남는다.
> **해법 A 가 먼저다.** B 는 그 위에 얹는 편의 기능으로 다룬다.

### 5-3. 그래도 B 를 만들 값어치 — 성능이 아니라 **작업 편의**

"여러 체인 중 원하는 한두 개만 흔들리게 보고 싶다" 는 것 자체가 유용한 기능이다. 성능 목적이
아니라 **보기 목적**으로 설계하면 된다. 다만 요청하신 `[0,1]` 실수형은 이 목적에 맞지 않는다.

| | `[0,1]` 실수 | **bool 토글 (권장)** |
|---|---|---|
| 0.5 의 뜻 | 정의할 수 없다 (평가를 "절반만" 멈출 수는 없다) | 해당 없음 |
| 이미 있는 것 | `windEnvelope` 가 이미 [0,1] 세기 조절이다 — **역할이 겹친다** | 겹치지 않는다 |
| 구동 방식 | 연결로 `nodeState` 를 못 몬다 | `setAttr` 로 명확 |

그래서 **`windMute` (bool, 기본 off)** 를 드라이버에 두고, 세기는 기존 `windEnvelope [0,1]` 이
그대로 맡는 구조를 제안한다. "0이면 끈다"는 요청의 **의도**(평가 자체를 멈춘다)는 그대로 살리되,
"세기 0" 과 "평가 중단" 이라는 서로 다른 두 개념을 한 어트리뷰트에 섞지 않는다.

> `[0,1]` 실수형을 그대로 원하시면 그렇게 만들 수 있다. `< 0.001` 이면 mute, 아니면 그 값을
> `windEnvelope` 로 넘기는 식이다. 다만 위 이유로 권하지 않는다 — **결정이 필요한 지점**이다.

### 5-4. 무엇을 끌 것인가

해법 A 이후에는 expression 이 없으므로, 끌 대상은 그 체인의 노드망 전체다.

- 제거 세트(`*_waveLiteSET`)가 **이미 체인별 노드를 전부 담고 있다.** 드라이버 이름 접두사로
  묶어 그 체인의 노드만 `nodeState` 를 바꾼다.
- 조인트의 `rotate` 채널 연결은 **끊지 않는다.** `nodeState=2 (Blocking)` 이면 마지막 값이
  유지되므로, mute 한 체인은 **그 순간 포즈로 멈춘다**(rest 로 돌아가지 않는다).
  rest 로 되돌리고 싶으면 `HasNoEffect` + rest 값 `setAttr` 이 필요하다 — **결정이 필요한 지점**.
- 디버그 커브도 같이 숨긴다(`visibility 0`). 뷰포트 그리기까지 줄이려면 이쪽이 실효가 크다.

## 6. 작업 계획

### 6-1. 1단계 — 표현식 제거 (해법 A) · **여기까지만 해도 목표 달성**

대상: `app/core/wind_manager.py`

1. `_make_phase_time_nodes(drv, start)` 신설 — `time1.outTime → addDoubleLinear → multDoubleLinear
   → addDoubleLinear → drv.windPhaseTime`, 만든 노드 리스트 반환.
2. `_make_phase_expression()` 은 **지우지 않고 남긴다.** 4-1 의 굽기에서 참조 구현으로 쓰고,
   기존 씬을 여는 경우의 하위호환 설명 근거로 둔다.
3. 세 드라이버 생성 함수에서 호출을 갈아 끼운다 — `wind_manager._make_driver`,
   `wave_manager._make_wave_driver`, `wave_lite_manager._make_lite_driver`.
   **세 탭이 같은 병을 앓고 있다**(Chain Wave 탭 30체인 = 14 fps 실측). 한 군데만 고치지 않는다.
4. 반환된 노드가 **제거 세트에 들어가야** `Remove` 로 같이 지워진다. 세 탭 각각 확인.
5. `bake`(Curve 출력) 경로는 노드망을 굽고 지우므로 그대로 동작해야 한다 — 회귀 확인 대상.

### 6-2. 2단계 — 가변 속도 (4-1 굽기 / 4-2 라이브 중 택일)

> 8절 결정 1 에서 **방법 1(통합 표현식)** 을 고르면 아래 대신 이렇게 된다:
> 빌드마다 표현식 **1개**를 만들어 그 빌드의 키 걸린 드라이버 전부의 `windPhaseTime` 을 계산하고,
> 상수 속도 드라이버는 6-1 의 노드 경로로 둔다(하이브리드). 표현식은 제거 세트에 넣어 `Remove`
> 로 함께 지운다. 드라이버를 개별 삭제하면 표현식이 깨지므로 **표현식 재생성 경로**가 필요하다.
> 아래 굽기 코드는 그 경우에도 `Rebuild Phase`(수동 확정용)로 남겨 둘 값어치가 있다.

1. `bake_phase_time(drv, start, end)` 를 `wind_manager` 에 신설. `windSpeed` 를 프레임 단위로
   읽어 사다리꼴 적분 → `windPhaseTime` 에 `setKeyframe`. **현행 표현식과 같은 식**을 쓴다.
2. 빌드 시 `windSpeed` 에 이미 키가 있으면 자동으로 굽는다(로그로 알린다).
3. UI 에 **`Rebuild Phase`** 버튼 — 씬의 드라이버(또는 선택한 것)를 다시 굽는다.
4. 구운 뒤에는 노드 경로 연결을 끊는다(둘이 동시에 `windPhaseTime` 을 물면 안 된다).

### 6-3. 3단계 — 체인 mute (해법 B, 선택)

1. 드라이버에 `windMute` (bool, 기본 off) 추가.
2. `set_chain_mute(driver, on)` — 그 체인의 세트 멤버 `nodeState` 일괄 변경 + 디버그 커브
   `visibility`.
3. UI: Chain Wave Lite 탭에 **`Solo` / `Mute All` / `Unmute All`** — TSL 에서 고른 체인만 남기고
   나머지를 끈다.
4. `Remove` 는 mute 상태와 무관하게 동작해야 한다(회귀 확인).

### 6-4. 하위호환

| | |
|---|---|
| **이미 만들어 둔 씬** | 표현식이 그대로 남아 계속 느리다. 문서에 **다시 빌드하라**고 명시하고, 가능하면 `Remove` → `Build` 를 권하는 안내를 로그에 넣는다. |
| **기존 씬 자동 변환** | 씬의 `*_windInteg` 표현식을 찾아 노드 경로로 갈아 끼우는 **`Upgrade Drivers`** 버튼도 가능하다 — 3단계와 함께 판단. |
| **결과 값** | 상수 속도는 **변하지 않는다**(실측 0.000e+00). 가변 속도도 굽기를 쓰면 동일. |

## 7. 이 진단의 한계 — 정직하게

- **헤드리스 측정이라 뷰포트 그리기 비용이 빠져 있다.** 위 숫자는 전부 DG 평가 시간이다.
  해법 A 로 DG 가 0.96 ms(50체인)까지 내려가면 남는 것은 그리기 비용인데, 그건 조인트/커브를
  화면에 그리는 비용이라 이 툴의 노드망과 무관하다. 실제 뷰포트에서 30 fps 가 안 나온다면
  그때는 **디버그 커브 끄기 · 조인트 표시 끄기**가 다음 카드다(→ 5-4).
- **다른 리그와 섞인 실제 프로덕션 씬에서는 재지 않았다.** 다른 무거운 것이 함께 있으면 그쪽이
  새 병목이 될 수 있다.
- 측정은 조인트 5개 체인 기준이다. 조인트 수는 비용과 무관함을 3~12 범위에서 확인했다(2절).

## 8. 결정이 필요한 지점

1. **가변 속도(`windSpeed` 키) 를 어떻게 지원할 것인가?** (→ 4-2 에 네 안을 실측 비교)
   - (a) **방법 1 · 통합 표현식** — 진짜 라이브, 30체인 1.35ms, 단 spline 에서 값 21% 차이 **(권장)**
   - (b) 방법 2 · 콜백 자동 재굽기 — 값 동일·최고 성능, debounce 필요 + 씬 저장 안 됨
   - (c) 방법 3 · `windPhaseTime` 직접 키잉 — 완전 라이브·비용 0, UI 개념이 바뀜
   - (d) 6-2 대로 수동 굽기 + `Rebuild Phase` 버튼 — 값 동일, 라이브성만 잃음
2. **mute 어트리뷰트를 `[0,1]` 실수로 할 것인가, bool 로 할 것인가?** (→ 5-3, bool 권장)
3. **mute 한 체인을 어떤 자세로 세울 것인가?** — `Blocking`(그 순간 포즈로 정지) vs
   `HasNoEffect` + rest 복원 (→ 5-4)
4. **3단계(mute)를 이번에 할 것인가?** 해법 A 만으로 목표 성능은 달성된다. mute 는 성능이 아니라
   **보기 편의**로서 값어치가 있다(→ 5-3).
5. **기존 씬 자동 변환(`Upgrade Drivers`) 을 넣을 것인가?** (→ 6-4)

## 9. 재현용 측정 스크립트

이 문서의 모든 숫자는 아래 순서로 다시 잴 수 있다.

```python
# mayapy (Maya 2024) 헤드리스
# 1) 체인 N개 x 조인트 5개를 만들고 build_wave_lite(output="node")
# 2) cmds.evaluationManager(mode="parallel")
# 3) cmds.currentTime(f) 를 프레임 80~100 에 대해 돌리고 경과/프레임수
# 4) 비교군: cmds.delete(cmds.ls(type="expression")) 후 같은 측정
#    또는 expression 의 nodeState 를 1/2 로
```

핵심 한 줄 확인 — **이 두 값의 차이가 이 문서 전부다.**

```python
cmds.delete(cmds.ls(type="expression"))   # 30체인 58.72 ms -> 0.10 ms
```
