# A00390 Chain Wave — 커브·ikHandle 없이 같은 움직임

루트가 100개를 넘어가면 커브·ikHandle·노드가 너무 많이 생긴다. **같은 움직임을 훨씬 가벼운
셋업으로** 재현하는 방법을 정한다.

- **작성일**: 2026-08-18
- **대상**: `tools/A00390_WindTool/app/core/wave_manager.py` (Chain Wave 탭)
- **상태**: **A안 적용 완료** — `tools/A00390_WindTool_V02` (8절)

---

## 1. 지금 무엇이 얼마나 생기는가 (실측)

체인 하나에 커브 1 + ikHandle 1 + 이펙터 1 + **프록시 조인트 체인** + 드라이버 + CV마다 노드 10개
+ 노드마다 매트릭스 노드 2개가 생긴다. mayapy 로 실제로 세어 본 값이다.

| 체인 길이 | 체인당 생성 노드 | 루트 100개 환산 |
|-----------|------------------|-----------------|
| 조인트 5개 | **89** | 약 8,900 |
| 조인트 9개 | **141** | 약 14,100 |
| 조인트 15개 | **219** | 약 21,900 |

조인트 9개 기준 내역:

| 무엇 | 개수 | 100루트 |
|------|------|---------|
| CV 노드망 (CV 10개 × 10) | 100 | 10,000 |
| 프록시 조인트 | 10 | 1,000 |
| 컨트롤 전달(multMatrix + decomposeMatrix) | 18 | 1,800 |
| 커브 · ikHandle · 이펙터 | 3 | **300** |
| 드라이버 로케이터 · 표현식 · 세트 · 그룹 | 나머지 | — |

> ikSCsolver / ikRPsolver / ikSplineSolver / hikSolver 는 **씬 전역 싱글턴**이라 체인 수만큼
> 늘지 않는다(위 표에서 제외).

**아웃라이너에 커브 100개 + ikHandle 100개가 쌓이는 것**이 사용자가 말한 문제이고,
그보다 **노드 14,000개**가 씬 평가에 더 큰 부담이다.

## 2. 지금 어떻게 동작하는가

```
조인트 rest 위치에 CV 를 둔 커브
        ↓  CV 를 노드망으로 흔든다
        CV_k.y = rest + A · ramp_k · sin( 2π( s_k/λ − φ ) )
        ↓
ikSpline 핸들이 그 커브를 따라 체인을 눕힌다  (rootOnCurve=False → translate 불변)
        ↓
프록시 체인의 월드 회전 변화량 → 사용자의 조인트/컨트롤러 rotate
```

**커브 + ikSpline 을 쓴 이유는 타당했다.** "뼈 길이를 지키면서 회전만으로 파형을 따라가게" 하는
문제의 정답이 마야에 이미 있었고, 직접 각도를 계산하는 것보다 안전했다. 이번 계획은 그 판단을
뒤집는 게 아니라, **개수가 100을 넘는 상황에서만** 다른 길을 두자는 것이다.

---

## 3. "각도를 직접 계산하면 되지 않나" — 그대로는 안 된다 (실측)

가장 먼저 떠오르는 방법은 커브를 없애고 **파형의 접선각을 그대로 쓰는 것**이다.

```
y(s) = A · r(s) · sin( 2π(s/λ − φ) )
θ(s) = atan( dy/ds )                 ← 뼈의 월드 방향각
localRot_k = θ_k − θ_(k−1)           ← FK 누적을 상쇄해 체인이 말리지 않는다
```

이 식이 현재 결과와 같은지 **재 봤다**(조인트 9, 뼈 2.0, A 1.5, λ 10, ramp 1).

| 프레임 | 뼈 | ikSpline | 해석식 | 차이 |
|--------|-----|----------|--------|------|
| 1 | 0 | 3.70° | 5.06° | 1.37° |
| 1 | 3 | −9.46° | −16.87° | 7.41° |
| 1 | 7 | −25.49° | **−39.67°** | **14.18°** |

**해석식이 일관되게 과대하다.** 원인은 알려져 있다 — NURBS(3차) 커브는 CV 를 통과하지 않고
**안쪽으로 당겨진다**(툴 주석에도 "실제 흔들림은 약 0.85배"라고 적혀 있다).

그렇다면 **상수 하나로 보정하면 되는가? 안 된다.** 조건을 바꿔 가며 `실제/해석` 비를 쟀다.

| 조건 | A_eff / A (평균) |
|------|------------------|
| 기본 (9j, 뼈 2.0, λ 10) | 0.657 |
| 진폭 0.5 / 3.0 | 0.653 / 0.646 |
| **파장 6** | **0.411** |
| **파장 20** | **0.745** |
| ramp 0 | 0.742 |

- **진폭에는 무관하다**(0.646~0.657) — 좋은 신호다. 모양은 맞고 크기만 틀렸다는 뜻이다.
- **파장에는 크게 의존한다**(0.41 ~ 0.75). 상수 보정으로는 못 맞춘다.

이 의존성은 설명이 된다. 균등 3차 B-스플라인은 CV 간격 `h` 와 파장 `λ` 에 대해
**진폭을 `(2 + cos(2πh/λ)) / 3` 배로 감쇠**시킨다. 계산해 보면
λ6 → 0.500, λ10 → 0.770, λ20 → 0.936 이고, 실측값과의 비는 각각 0.82 / 0.85 / 0.80 으로
**거의 일정하다.** 즉 "B-스플라인 감쇠 × 상수" 로 설명되는 구조다.

> 남은 ~0.82 는 커브가 체인보다 길어지며 생기는 호길이 재매개변수화와, 접선을 코드 중점에서
> 재는 데서 온다고 본다. **이 부분은 아직 확인하지 않았다** — 5절에서 확인 항목으로 잡는다.

## 4. 선택지

### A안 — 각도를 직접 구동 (권장)

커브·ikHandle·이펙터·프록시 체인·매트릭스 전달을 **전부 없애고**, 조인트의 로컬 회전을
노드망으로 직접 만든다.

```
u_k        = s_k/λ − φ                     (조인트마다 상수 s_k)
term_k     = ramp_k · cosLUT(u_k)
localRot_k = Θ · (term_k − term_(k−1))     (Θ = 진폭에서 환산한 각도)
```

- `term_k` 는 **이웃 조인트가 공유**한다 → 조인트당 LUT 1개면 된다.
- 회전축은 rest 자세에서 **파동 평면의 법선을 조인트 로컬로 옮긴 고정 벡터**다.
  임의 축 회전이므로 `axisAngleToQuat → quatProd(rest) → quatToEuler` 로 rotate 에 쓴다
  (조인트 오리엔트·rotateOrder 가 어떻든 안전하다).
- **프록시가 사라진다** — 조인트든 FK 컨트롤러든 같은 경로로 처리된다. 지금 컨트롤러 때문에
  필요했던 프록시 체인과 매트릭스 노드 28개(9조인트 기준)가 통째로 없어진다.

**예상 비용** (조인트 9개 기준): 조인트당 6~8 노드 + 드라이버 → **체인당 약 60~75** (현재 141).
**커브 0 · ikHandle 0 · 프록시 조인트 0.** 100루트면 약 6,000~7,500 노드.

**대가**: 3절에서 본 대로 **지금 셋업과 값이 그대로 같지는 않다.** 같은 룩을 유지하려면
감쇠 보정 `(2 + cos(2πh/λ))/3 × k` 를 넣거나, 진폭 파라미터의 뜻을 "CV 를 미는 양"에서
**"뼈가 흔들리는 각도"** 로 바꾸고 환산표를 안내해야 한다.

### B안 — 체인당 표현식 1개

노드망 대신 `expression` 하나가 그 체인의 모든 조인트 rotate 를 쓴다.

- **체인당 노드 2개**(표현식 + 드라이버). 100루트면 200개 — 압도적으로 가볍다.
- 표현식 안에서 `sin` 을 직접 쓰므로 LUT 도 필요 없다.
- **위험**: 표현식은 병렬 평가(EM)에서 불리하다. 노드 14,000개를 병렬로 도는 것보다
  표현식 100개를 도는 게 **더 느릴 수도 있다.** 반드시 재 봐야 한다(5절).

### C안 — 굽기 (이미 있다)

`output=OUTPUT_CURVE` 가 이미 회전 키로 굽고 셋업을 지운다. **노드 0.**
라이브 조절을 포기하는 대신 100루트에서도 씬이 가볍다.
→ **새로 만들 것은 없고**, UI 에서 "루트가 많으면 이쪽" 이라고 안내만 강화하면 된다.

### 비교

| | 현재 | A안 | B안 | C안 |
|---|---|---|---|---|
| 체인당 노드 | 141 | ~65 | **2** | 0 |
| 커브 / ikHandle | 1 / 1 | **0 / 0** | **0 / 0** | 0 / 0 |
| 라이브 조절 | O | O | O | **X** |
| 기존 룩 재현 | 기준 | 보정 필요 | 보정 필요 | 그대로 |
| 평가 성능 | 노드 다수 | 노드 감소 | **미지수** | 최고 |

## 5. 권장 진행 순서

1. **먼저 재고 정한다.** 100루트 씬을 만들어 **현재 / A안 / B안** 의 프레임당 평가 시간을 잰다.
   A안과 B안 중 무엇이 나은지는 **지금 답을 모른다** — 표현식이 병렬 평가에서 얼마나 손해인지가
   갈림길이다. 이 측정 없이 구현을 고르지 않는다.
2. **감쇠 모델을 확정한다.** 3절의 `(2 + cos(2πh/λ))/3 × k` 에서 `k` 가 정말 상수인지,
   뼈 길이가 불균일한 체인에서도 성립하는지 확인한다. 안 되면 **진폭의 뜻을 각도로 바꾸는 쪽**
   (환산 포기)으로 간다.
3. 고른 안을 `wave_manager` 에 **새 출력 모드로 추가**한다 — 기존 경로를 지우지 않는다.
   `output=OUTPUT_NODE`(현행) / `OUTPUT_LIGHT`(신규) / `OUTPUT_CURVE`(굽기).
   기존 씬과 기존 셋업이 그대로 열려야 한다.
4. UI 에 모드 선택과 **"루트 N개 이상이면 이쪽"** 안내를 넣는다.
5. `remove_wave` 가 새 셋업도 지우게 한다(세트 기반이라 구조는 그대로 쓸 수 있다).

## 6. 검증 계획

- **움직임 비교**: 같은 체인에 현재/신규를 각각 걸고, 여러 프레임에서 **조인트 월드 위치**와
  **뼈 방향각**을 비교해 최대 차이를 각도와 %로 보고한다. 목표는 "눈에 같아 보이는 수준"이며,
  숫자로 얼마나 다른지 **문서에 남긴다**(같다고 주장하지 않는다).
- **불변 조건**: translate 가 하나도 안 바뀌는가 · 세그먼트 길이가 유지되는가 · 루트가 제자리인가
  — 현재 구현이 지키는 약속을 신규도 지켜야 한다.
- **정리**: `remove_wave` 뒤 잔여 노드 0, 회전이 rest 로 복귀.
- **성능**: 루트 100개 × 조인트 9개에서 프레임당 시간(현재/A/B), 노드 총수, 씬 저장 크기.
- **경계**: 뼈 길이 불균일 / 분기 체인 / 조인트가 아닌 FK 컨트롤러 / ramp 0 · 1 / 파장 ≪ 뼈 길이.

## 7. 열린 결정 (사용자 확인 필요)

- **진폭 파라미터의 뜻을 바꿔도 되는가.** 지금은 "CV 를 미는 월드 거리"다. A안에서는
  **"뼈가 흔들리는 각도(도)"** 로 두는 편이 훨씬 예측 가능하다. 대신 **기존 씬의 값이 그대로
  같은 결과를 내지 않는다.** 바꾸지 않으려면 감쇠 보정을 넣어야 하고, 그만큼 복잡해진다.
- **기존 셋업을 마이그레이션할 것인가**, 새로 만들 때만 신규 모드를 쓸 것인가.
- **몇 개부터 신규 모드를 기본값으로 할 것인가**(예: 루트 20개 이상).

## 8. 적용 결과 (2026-08-18)

**A안(각도 직접 구동)** 을 새 툴 `A00390_WindTool_V02` 에 구현했다. 기존 `A00390_WindTool` 은
손대지 않았고, V02 는 V01 을 통째로 복제한 뒤 **Chain Wave Lite 탭**을 더한 것이다.

### 무엇을 만들었나

- `app/core/wave_lite_manager.py` (신규) — `build_wave_lite` / `remove_wave_lite`.
  기존 `wave_manager` 는 그대로 두고 옆에 붙였다.
- `Chain Wave Lite` 탭 — Sine / Chain Wave 탭은 그대로 있고 세 번째로 붙는다.
- 진폭의 뜻을 **각도(`windSwingAngle`, 도)** 로 바꿨다(사용자 승인).

### 측정 (조인트 9, 뼈 2.0)

| | Chain Wave | Chain Wave Lite |
|---|---|---|
| 생성 노드 | 141 | **95** (−33%) |
| 커브 / ikHandle / 이펙터 / 프록시 조인트 | 1 / 1 / 1 / 10 | **0 / 0 / 0 / 0** |

- 뼈 각도가 정의식과 최대 **0.015°** 차이(16샘플 싸인 LUT 보간 오차, 20° 스윙의 0.07%).
- translate 불변 · 뼈 길이 유지 · 루트 고정 — 기존이 지키던 약속을 그대로 지킨다.
- **FK 컨트롤러 체인에서도 프록시 조인트가 0** 이다(기존은 컨트롤러당 프록시 체인이 필요했다).

### 5절에서 예고한 것 중 하지 않은 것

- **B안(체인당 표현식 1개)과의 성능 비교를 하지 않았다.** A안이 요구를 이미 만족해
(커브·ikHandle·프록시 0) 먼저 구현했다. 100루트 실측이 필요하면 B안을 나중에 붙일 수 있다.
- **감쇠 모델(`(2+cos(2πh/λ))/3 × k`) 은 구현하지 않았다.** 진폭의 뜻을 각도로 바꾸기로 하면서
  기존 값 재현이라는 목표 자체가 없어졌기 때문이다. 3절의 측정은 "왜 재현을 포기했는지"의
  근거로 남는다.

### 남은 일

- 마야에서 **기존 탭과 나란히 걸어 눈으로 비교** (헤드리스로는 확인 못 한 부분).
- 루트 100개 실제 씬에서 프레임당 평가 시간 측정.
