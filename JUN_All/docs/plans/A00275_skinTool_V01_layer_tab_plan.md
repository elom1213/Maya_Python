# A00275_skinTool_V01 — Layer 탭 계획서

> **목적**: 토폴로지가 같은 메시 **N 개**(M_01, M_02, M_03 …)가 각자 다른 조인트에 바인드돼 있을 때,
> 메시마다 **보존할 조인트(lock)** 와 **섞을 양(Blend)** 을 정해 `Merge` 하면, 그 규칙대로 웨이트가
> 합성된 **새 메시 `M_new`** 를 만든다.

- **작성일**: 2026-09-15
- **대상**: `tools/A00275_skinTool_V01` — 신규 `app/core/weight_layer_manager.py` + `app/ui/main_window.py`
- **상태**: **구현 — v01.22 (2026-09-15).** 10장 답 반영: Q1 계획대로 · **Q2 베이스 lock 허용 + 재정규화** ·
  **Q3 규칙 ②(lock 절대값 보존, 넘친 곳은 위 레이어부터 자름 — v01.22 는 "위 레이어 우선" 으로 반대로 구현했다가
  사용자 피드백으로 v01.23 에서 바로잡음)** · Q4 메시는 겹쳐 있고 조인트는 다름, 형상은 맨 아래 ·
  Q5 순서 동일 가정. 추가 요청: **Update existing mesh 모드**, 조인트 **다중 선택·다중 체크**(Shape Editor 식),
  `Weights > Layer`. 2장의 식은 규칙 ① 기준이라 **실제 구현 규칙은 가이드 문서 `A00275_skinTool_V01.md` 의 Layer 절**을 볼 것.
- **버전**: v01.21 → **v01.22**
- **선례**: `Weights > Copy Weights` 의 Blend(볼록결합이라 정규화가 안 깨진다),
  `Bind > Bind Pose`(`bindPreMatrix` 를 직접 다루는 법), `Weights > Transfer`(여러 소스 메시 리스트)

## 1. 요청 정리

사용자 예시 (메시 2개):

| 메시 | 바인드된 조인트 | lock | Blend |
|---|---|---|---|
| M_01 | jnt_01_a, jnt_01_b, jnt_01_c | **jnt_01_a, jnt_01_b** | 1 |
| M_02 | jnt_02_a, jnt_02_b, jnt_02_c | (없음) | 1 |

`Merge` 결과 `M_new`:

- jnt_01_a, jnt_01_b 에 바인드되고 **그 두 조인트의 웨이트는 M_01 과 같다.**
- M_01 에서 **jnt_01_c 가 차지하던 몫**에는 jnt_02_a/b/c 가 **M_02 에서와 같은 비율로** 들어간다.
- jnt_01_c 는 `M_new` 의 인플루언스가 아니다.
- **메시가 3개 이상이어도 똑같이 동작해야 한다** (추가 요청).

## 2. 정의 — "레이어 합성"

리스트의 **위쪽이 우선순위가 높은 레이어**, **맨 아래가 베이스**다(포토샵 레이어와 같은 방향).

버텍스 v 하나에 대해, 레이어 i 의 기호:

| 기호 | 뜻 |
|---|---|
| `w_i` | 레이어 i 메시의 웨이트 행 (인플루언스별 값, 합 1) |
| `K_i` | 레이어 i 에서 lock 한 조인트 집합 |
| `P_i` | `w_i` 중 **lock 한 조인트의 값만** 남긴 행 |
| `L_i` | `P_i` 의 합 = lock 한 조인트가 차지하는 몫 (0~1) |
| `b_i` | Blend (0~1) |

### 2-1. 위에서 아래로 "남은 몫" 을 넘긴다

```
r = 1                                   # 아직 아무도 차지하지 않은 몫
for i = 1 .. N-1 (위 -> 아래, 베이스 제외):
    M_new += r * b_i * P_i              # 이 레이어가 가져가는 양
    r     *= (1 - b_i * L_i)            # 남은 몫
M_new += r * w_N                        # 베이스가 나머지를 자기 비율대로 채운다
```

같은 식을 아래에서 위로 쓰면 **"over" 합성**(알파 = `b_i · L_i`)이다:
`C_N = w_N`, `C_i = b_i·P_i + (1 − b_i·L_i)·C_(i+1)`. 두 표현은 값이 같다.

### 2-2. 이 정의가 주는 성질

- **정규화가 저절로 유지된다.** 각 단계에서 가져간 양 `r·b_i·L_i` 와 남긴 양
  `r·(1 − b_i·L_i)` 의 합이 `r` 이라, 입력 행이 합 1 이면 결과도 **정확히 1** 이다.
  마야에게 정규화를 맡기지 않는다(`normalize=False`) — Copy Weights 의 Blend 와 같은 이유.
- **Blend = 1, 레이어 2개면 요청과 정확히 같다.** 위 레이어의 lock 값은 그대로, 나머지 몫
  `1 − L_1` 에 베이스 행이 비율대로 들어간다.
- **Blend = 0 이면 그 레이어가 없는 것과 같다.** 0.5 면 lock 몫의 절반만 가져가고 나머지 절반은
  아래로 흘러간다.
- **N 개로 그대로 확장된다.** 레이어가 늘어도 식은 한 줄씩 늘 뿐이다.

### 2-3. 숫자 예시

**(A) 요청 예시 — 버텍스 하나** (`M_01 = a .5 / b .2 / c .3`, `M_02 = a .1 / b .6 / c .3`)

| Blend(M_01) | 01_a | 01_b | 02_a | 02_b | 02_c | 합 |
|---|---|---|---|---|---|---|
| 1.0 | .50 | .20 | .03 | .18 | .09 | 1.00 |
| 0.5 | .25 | .10 | .065 | .39 | .195 | 1.00 |

1.0 일 때: jnt_01_c 가 차지하던 .3 을 M_02 의 비율(.1/.6/.3)대로 나눴다.

**(B) 레이어 3개** — M_01 은 `01_a`(.4) lock, M_02 는 `02_b`(.5) lock, M_03 은 베이스(`03_a` 1.0). Blend 전부 1.

```
M_01 : 01_a 를 .4 가져감          남은 몫 .6
M_02 : 02_b 를 .6 x .5 = .3 가져감  남은 몫 .6 x .5 = .3
M_03 : 나머지 .3 을 03_a 로
결과 : 01_a .4 / 02_b .3 / 03_a .3
```

> [!warning] 아래 레이어의 lock 값은 **위 레이어가 비워 둔 만큼만** 보존된다
> (B) 에서 M_02 는 `02_b` 를 .5 로 lock 했지만 결과는 **.3** 이다. 위의 M_01 이 이미 .4 를
> 가져갔기 때문이다. **메시가 3개 이상일 때 리스트 순서가 결과를 바꾼다.**
> 이게 원하는 동작인지는 10장 Q3 에서 확인한다(다른 규칙도 적어 두었다).

## 3. M_new 를 만드는 법

### 3-1. 인플루언스

- **베이스가 아닌 레이어**: lock 한 조인트만.
- **베이스**: 자기 조인트 전부.
- 합성 결과가 **전 버텍스에서 0 인 조인트는 넣지 않는다**(로그에 개수).
- **같은 조인트가 여러 레이어에 있으면**(센터 조인트 공유 등) 한 열로 **더한다.**

### 3-2. 바인드 행렬 — 지금 포즈로 다시 바인드하지 않는다

`skinCluster` 를 새로 만들면 마야는 **현재 조인트 위치**를 바인드 포즈로 삼는다.
두 리그가 바인드 포즈가 아닌 상태면 `M_new` 가 만드는 순간 튄다.

- 인플루언스마다 **그 조인트를 가져온 레이어의 skinCluster** 에서 `bindPreMatrix[논리 인덱스]` 를
  읽어 `M_new` 의 skinCluster 에 **그대로 써 넣는다**(`maya_skin.logical_indices()` — 플러그를 직접
  다룰 때는 논리 인덱스).
- 같은 조인트가 두 레이어에 있는데 `bindPreMatrix` 가 다르면 **위 레이어 값을 쓰고 경고**한다.
- `geomMatrix` 는 지오메트리를 가져온 레이어의 것을 쓴다. `dagPose` 는 새로 만든다
  (`bind_pose_manager._rebuild_bind_pose` 재사용 검토).
- `skinningMethod` · `maxInfluences` 등 설정은 베이스를 따르고, 레이어끼리 다르면 로그로 알린다.

### 3-3. 지오메트리

- 기본은 **베이스 메시의 rest 셰이프**(skinCluster 입력 쪽 형상)를 복제한다. 출력(변형된) 형상을
  복제하면 현재 포즈가 구워진다.
- skinCluster **앞의 디포머**(blendShape 등)는 따라오지 않는다 — `M_new` 는 스킨만 가진다.

### 3-4. 웨이트 쓰기

- 레이어마다 `MFnSkinCluster.getWeights` 로 **한 번에** 읽는다(물리 인덱스 — `maya_skin.influence_paths()`
  의 열 순서).
- 합성은 **0 이 아닌 값만** 도는 희소 계산(버텍스 × 레이어 × 행의 0 아닌 수)이다.
- `setWeights(..., normalize=False)` 한 번으로 쓴다.
- 입력 행의 합이 1 이 아니면(`normalizeWeights` 가 꺼진 메시) **읽을 때 정규화**하고 개수를 알린다.
  정규화하지 않으면 2-2 의 보장이 깨진다.

### 3-5. 검증 — 합성 전에 막는다

| 검사 | 실패 시 |
|---|---|
| 레이어가 2개 이상 | 실행 안 함 |
| 모든 메시에 skinCluster 가 있다 | 그 메시 이름과 함께 실행 안 함 |
| **버텍스 수가 같고 페이스 연결(`MFnMesh.getVertices`)이 같다** | 실행 안 함 — 순서가 다르면 인덱스 합성이 조용히 틀린다. Transfer 탭을 쓰라고 안내 |
| 베이스가 아닌 레이어에 lock 이 하나도 없다 | 경고(그 레이어는 아무것도 기여하지 않는다) |
| 같은 메시가 두 번 올라왔다 | 실행 안 함 |

위치(버텍스 좌표)는 비교하지 않는다. 다만 **다르면 경고**한다 — 이유는 10장 Q4.

## 4. UI — `Weights > Layer`

메시가 N 개라 메시마다 박스를 쌓으면 금방 길어진다. **위는 레이어 목록, 아래는 고른 레이어의
상세**(마스터-디테일) 구조로 한다.

```
┌ Layers (top = highest priority, bottom = base) ─────────────┐
│  #  Mesh      Locked   Blend                                │
│  1  M_01      2 / 3    1.00                                 │
│  2  M_02      base     -                                    │
│  [Add Selected] [Remove] [Up] [Down] [Clear]                │
└─────────────────────────────────────────────────────────────┘
┌ Joints : M_01 ──────────────────────────────────────────────┐
│  Filter [            ]                                      │
│  [x] jnt_01_a                                               │
│  [x] jnt_01_b                                               │
│  [ ] jnt_01_c                                               │
│  [Lock Selected] [Unlock Selected] [Lock All] [Unlock All]  │
│  [Select Joints]                                            │
│  Blend [1.00] ────────────●                                 │
└─────────────────────────────────────────────────────────────┘
┌ Output ─────────────────────────────────────────────────────┐
│  Name [M_new          ]   Geometry from [Base ▼]            │
└─────────────────────────────────────────────────────────────┘
[                          Merge                             ]
```

- **레이어 목록**: `QTreeWidget` 3열. 순서 = 우선순위. 맨 아래 줄은 `base` 로 표시하고 lock / Blend 를 끈다.
  `Up` / `Down` 으로 순서를 바꾸면 베이스 표시도 따라간다.
- **조인트 목록**: 체크박스가 lock. 조인트가 수백 개인 리그를 생각해 공용 `MOD_filter_qt_v01` 의
  트리 모드를 붙인다. `ItemIsUserCheckable` 은 기본 ON 이라 플래그로 판정하지 않는다.
- **Blend**: `QDoubleSpinBox`(0~1) + 슬라이더. 스핀박스는 `setKeyboardTracking(False)`.
- 레이어 상태(메시 · lock 집합 · Blend)는 **툴이 들고 있다.** 마야 조인트의 `lockInfluenceWeights` 는
  건드리지 않는다(10장 Q6).
- 메시는 UUID 로 보관한다(리네임·동명 대비, 공용 TSL 과 같은 원칙).
- 모든 UI 문자열은 영어.

## 5. 코어 모듈 — `app/core/weight_layer_manager.py`

UI 비의존. 위젯에서 읽은 값만 받는다.

|---|---|

## 8. 성능

- 비용은 `버텍스 × Σ(행의 0 아닌 값 수)`. 보통 한 버텍스에 인플루언스가 4~8개라 50,000 버텍스 × 레이어 3
  이면 수백만 번 연산 수준이다. 순수 파이썬으로 먼저 재 보고, 느리면 레이어별 열 단위 계산으로 바꾼다.
- 읽기·쓰기는 API 벌크 한 번씩이다(`skinPercent` 루프 금지).

## 10. 구현 전에 사용자에게 확인할 것

### 꼭 답이 필요한 것

**Q1. 부분 웨이트일 때 채우는 방식 (2-3 (A) 표).**
jnt_01_c 가 .3 인 버텍스에 M_02 의 행을 **.3 배로 줄여서** 넣는다(`02_a .03 / 02_b .18 / 02_c .09`).
이 방식이어야 jnt_01_a, jnt_01_b 의 값이 M_01 과 **정확히 같게** 남는다.
(M_02 행을 그대로 넣고 전체를 다시 정규화하면 jnt_01_a/b 값도 같이 줄어든다.) — **이 방식이 맞는가?**

**Q2. 맨 아래(베이스) 레이어의 lock / Blend.**
예시에서 M_02 는 lock 이 없는데도 조인트 3개가 전부 쓰였다. 그래서 계획은
"**맨 아래 레이어는 자기 조인트 전부로 나머지를 채운다**(lock · Blend 비활성)" 이다.
베이스에도 lock 을 걸어 일부 조인트만 쓰고 싶은 경우가 있는가? 있다면 채우지 못한 몫은
어떻게 할지(남은 조인트에 비율대로 재정규화 등) 정해야 한다.

**Q3. 메시가 3개 이상이고 lock 이 겹칠 때 (2-3 (B)).**

| 규칙 | (B) 결과 | 성질 |
|---|---|---|
| **① 위 레이어 우선, 남은 몫에 비율로** (현재 계획) | 01_a .4 / 02_b .3 / 03_a .3 | 연속적 · 순서가 의미를 가짐 · 아래 lock 값은 줄어들 수 있다 |
| ② lock 값은 절대값 보존, 합이 1 을 넘는 곳만 위 레이어 우선으로 자름 | 01_a .4 / 02_b .5 / 03_a .1 | lock 값이 더 문자 그대로 남지만, 합이 1 을 넘기 시작하는 경계에서 **웨이트가 꺾인다** |

메시 2개일 때는 두 규칙이 **같은 답**이다. 3개 이상에서 어느 쪽을 원하는가?

**Q4. 메시와 조인트가 공간상 겹쳐 있는가?**
`M_new` 는 한 자리에 있는데 jnt_01_* 와 jnt_02_* 에 동시에 바인드된다. 스키닝은 조인트의
**피벗을 중심으로** 버텍스를 돌리므로:
- M_01 과 M_02(와 각자의 스켈레톤)가 **같은 자리에 겹쳐 있으면** → 결과가 올바르다.
- **옆으로 떨어져 있으면**(M_02 가 x+100 에 있는 식) → rest 포즈에서는 멀쩡해 보이지만,
  jnt_02_a 를 돌리는 순간 `M_new` 의 버텍스가 **100 떨어진 피벗을 중심으로** 돌아 크게 틀어진다.

어느 경우인가? 떨어져 있다면 "합성 전에 한 자리에 겹쳐 둬야 한다" 는 제약으로 갈지, 다른 방법이
필요한지 정해야 한다. 함께 **`M_new` 형상을 어느 메시에서 가져올지**(기본: 베이스)도 확인.

**Q5. 메시들이 정말 같은 버텍스 순서인가?**
같은 메시를 복제해 각각 바인드한 것이면 된다. 따로 모델링·익스포트했거나 FBX 왕복 등으로
**버텍스 번호가 바뀌었을 수 있으면** 인덱스 합성이 조용히 틀린다(계획은 연결 구조 비교로 거절).

## 11. 검증 계획 (mayapy)

1. **요청 예시 재현** — 메시 2개, lock {01_a, 01_b}, Blend 1: jnt_01_a/b 열이 M_01 과 `1e-9` 이내로 같고,
   나머지 몫이 M_02 비율과 같다. jnt_01_c 는 인플루언스에 없다.
2. **N = 3** — 2-3 (B) 값 일치, 순서를 바꾸면 결과가 바뀌는 것 확인.
3. **Blend 0 / 0.5 / 1** — 0 이면 그 레이어가 없는 결과와 동일, 모든 행 합 1.
4. **변형 일치** (메시가 겹친 경우) — 조인트를 포즈시킨 뒤, `L_1 = 1` 인 버텍스는 M_01 의 변형 위치,
   `L_1 = 0` 인 버텍스는 M_02 의 변형 위치와 같다. **숫자 비교가 아니라 실제 디포메이션 비교.**
5. **바인드 포즈가 아닐 때 Merge** — 조인트를 돌린 상태에서 Merge 해도 `M_new` 가 튀지 않는다(`bindPreMatrix` 복사 확인).
6. **공유 조인트** — 두 레이어가 같은 조인트를 가지면 열이 더해진다.
7. **거절** — 버텍스 수 다름 · 연결 다름 · 스킨 없음 · 레이어 1개 · 중복 메시.
8. **정규화 안 된 입력** — 읽을 때 정규화하고 결과 합 1.
9. **undo** — Ctrl+Z 한 번에 `M_new` 와 skinCluster 가 사라진다.
10. **UI 스모크** — 레이어 추가/순서/베이스 표시, lock 체크, Blend, Merge 버튼과 로그.
