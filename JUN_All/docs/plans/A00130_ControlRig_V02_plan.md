## 3. 진단 상세 — B (아바타 조인트 이름) 보류

**보류해도 됩니다.** B 가 필요했던 이유는 **하나뿐**이었다 — 5단계 driver↔bind 자동 짝짓기(1-6 으로 철회).

나머지 단계에서 아바타 조인트 이름을 볼 일이 없는지 확인했다.

| 단계 | 아바타 이름이 필요한가 | 왜 |
|---|---|---|
| Template 생성 | ❌ | 조인트를 만들기만 한다 |
| Template 배치 | ❌ | **사람이 손으로 옮긴다**(1-3) |
| Orient | ❌ | 템플릿 자기 자신만 본다 |
| Validate | ❌ | 템플릿·케이지만 본다 |
| Controllers 매칭 | ❌ | **템플릿**을 타깃으로 쓴다 (V01 은 아바타 조인트를 썼지만 V02 는 템플릿이 대신한다) |
| Pose | ❌ | 케이지 내부 연결만 본다 |

> **이것이 템플릿 패러다임의 부수 효과다.** 템플릿이 아바타와 툴 사이에 끼어들면서
> **툴이 아바타를 전혀 몰라도 되는 상태**가 됐다. 아바타가 무엇이든, 이름이 무엇이든 상관없다.

**잔여 위험 (수용)**

- Validate 가 "driver 조인트가 bind 조인트를 다 덮고 있는가" 를 **점검할 수 없다** → Connect 는
  `A00145` 에서 사람이 하므로 그쪽 책임
- 나중에 짝짓기 자동화를 원하시면 **그때 B 가 다시 필요**해진다

## 4. 진단 상세 — D (ikHandle 세트 이름)

**세트 이름 하나면 충분합니다.** 이유: **IK 에 필요한 정보가 전부 씬에서 역산된다.**

### 4-1. 세트 이름 하나로 얻어지는 것

| 필요한 것 | 어떻게 얻나 | 검증됨 |
|---|---|---|
| 편집할 핸들 목록 | 세트 멤버 | — |
| **각 핸들의 조인트 체인** | `ikHandle -q -jointList` + 이펙터로 끝 조인트 역산 | ✅ `A00060` `chain_joints()` — **`jointList` 는 끝 조인트를 빼고 준다**는 함정까지 처리돼 있다 |
| 솔버 | `ikHandle -q -solver` | ✅ |
| 기존 폴 벡터 컨스트레인트 | `listConnections(h.poleVectorX, type="poleVectorConstraint")` | ✅ `pole_vector_constraint()` |
| **편집을 막는 요인** | `inspect(handle)` → `blockers` / `notes` | ✅ 커브 솔버 · 이펙터 없음 · 폴 벡터가 컨스트레인트가 아닌 것 · 일직선 체인 |
| **폴 타깃** | 컨스트레인트에서 유도 | ✅ `pole_vector_targets()` = `poleVectorConstraint(con, q=True, targetList=True)` |

> **폴 타깃도 씬에서 나온다.** `A00060` 이 타는 모든 경로가 이미 그렇게 하고 있다 —
> `end_edit(pv_mode="offset")` 은 **기존 컨스트레인트의 offset 만** 갱신하므로 타깃 이름을
> 알 필요조차 없고, 타깃을 옮기는 `pv_mode="target"` 조차 `targetList` 쿼리로 찾는다.
>
> **함정**: `listConnections("con.target[0]")` 는 **`None` 을 돌려준다** — 마야가 연결을
> **노드 단위로** 열거하기 때문이다. 반드시 `targetList` 쿼리를 쓴다
> (`constraint-target-plugs-and-offset-spaces`).

### 4-2. `helper_pvtgt` 를 만들지 않기로 한 이유 (2026-08-27 철회)

2차 개정에서는 각 `ikHandle` 에 `helper_pvtgt` 어트리뷰트를 달아 **붙어야 할** 폴 타깃을
연결해 주기로 했었다. **철회한다.**

컨스트레인트를 타고 들어가면 **지금 붙어 있는** 타깃을 알 수 있고, 어트리뷰트가 더해 주는 것은
**의도 vs 실제**의 차이뿐이다. 그 차이가 값어치를 갖는 경우는 셋인데 —

| 경우 | `helper_pvtgt` 없이 되나 |
|---|---|
| 컨스트레인트가 **아예 없다** | ✅ Validate 가 "폴 벡터 컨스트레인트가 없다" 고 말할 수 있다. **어느 오브젝트였어야 하는지**만 못 말한다 |
| **엉뚱한** 오브젝트를 가리킨다 | ❌ 대조할 기준이 없어 못 잡는다 |
| 폴 벡터를 컨스트레인트가 **아닌 것**이 구동한다 | ✅ `inspect()` 가 이미 blocker 로 잡는다 |

가운데 한 줄을 위해 어트리뷰트를 두는 값이 비용보다 크지 않다.

- **케이지는 리거가 만들어 고정한다**(1-1). 폴 타깃이 틀렸다면 그건 **케이지에서 고칠 문제**지
  툴이 대조해 줄 문제가 아니다.
- **진실의 원천이 둘이 되면 어긋난다.** 어트리뷰트가 A 를, 컨스트레인트가 B 를 가리킬 때
  **툴은 어느 쪽이 맞는지 판단할 수 없다** — 경고밖에 못 하는데, 그 경고는 어트리뷰트가
  없었으면 애초에 존재하지 않았을 문제다.
- 케이지 저작 부담이 핸들 수만큼 늘어난다.

> **나중에 다시 꺼낼 조건**: "컨스트레인트가 없는 핸들을 툴이 **복구**해 준다" 를 원하게 되면,
> 그 기능이 생기는 순간 이 어트리뷰트가 값어치를 갖는다. 지금은 아니다.
>
> 2차 개정에서 이것을 "Validate 용으로 값어치가 크다" 고 적었던 것은 과했다 —
> Validate 가 실제로 잡아야 할 항목은 어트리뷰트 없이 전부 잡힌다.

### 4-3. 유일하게 못 구하는 것 — **핸들의 "부위 귀속"** ⚠

세트에 든 핸들이 **어느 부위(Arm Left / Leg Right …)의 것인지**는 세트 이름만으로는 모른다.
이게 필요한 경우는 **하나뿐** — 사용자가 체크박스로 **일부 부위만** 빌드할 때.

**해결 3안 (추가 자료 없이 해결 가능)**

| 안 | 방법 | 비용 |
|---|---|---|
| **A. 전역 트랜잭션** | 부위와 무관하게 **모든 핸들을 한 번에 열고 → 옮기고 → 닫는다** | 없음. **어차피 7-4 에서 권장하는 방식** |
| **B. 체인 조인트로 판정** | 핸들의 체인 조인트가 그 부위의 케이지 세트 멤버인지 본다 | 없음 (자료 A 로 확인 가능) |
| **C. 핸들 이름 토큰** | 핸들 이름에 `A01_Arm_L` 같은 부위 토큰이 있으면 그걸로 | 없음 |

→ **A 를 기본으로 하고, B·C 를 부위별 필터로 얹는다.** 추가로 주실 자료는 없습니다.

> **한 줄만 확인 부탁**: 핸들 이름에 부위를 알아볼 토큰이 들어가나요? 들어가면 C 가 공짜로 붙습니다.

### 4-4. FK/IK 스위치 — D 에 **한 줄만** 덧붙여 주시면 좋습니다

1-5 로 `ikBlend` 가 스위치에 물려 있을 가능성이 큽니다. 그러면 IK Edit 이 **씬 전역 폴백**을 탑니다(7-4).
→ **스위치 어트리뷰트가 무엇인지**(예: `OptionAll_xx_ctl.FKIK_Arm_L`) 한 줄이면 충분합니다.
알면 툴이 **전역 폴백 대신 스위치를 직접 0 으로 내렸다 복원**할 수 있어 훨씬 안전해집니다.

> 오른팔 길이가 지금까지 **조용히 안 써지고 있었다**는 뜻입니다
> (`setAttr` 은 없는 어트리뷰트에 `RuntimeError` 를 냅니다).

**잔여 구멍 하나**: **스파인·손가락에는 측정이 없습니다.** V01 이 재지 않습니다.
스파인도 늘어남 세팅이 필요하다면 그때 어트리뷰트 이름을 주시면 됩니다.

### 5-2. G (작업 녹화) — **보류해도 제작 가능**

범위가 **V01 코드 + 확정된 5단계**로 완전히 특정된다. 녹화가 필요했던 이유는

## 7. 설계 판단 — 개선점 · 대안점

### 7-1. 템플릿을 **파일로 저장**한다 ★ (유지)

배치를 손으로 하기로 했으므로(1-3) **저장/로드의 값어치가 오히려 커졌다.**
손으로 놓은 결과를 잃으면 그 노동이 통째로 날아가기 때문이다.

→ **`<avatar>_template.json` 저장/로드**. 얻는 것:

- 씬을 잃어도 처음부터 하지 않는다
- 비슷한 체형에 **재사용**한다 (부분 로드도)
- `diff` 로 **무엇이 바뀌었는지** 본다 — 리그가 틀어졌을 때 원인 추적
- 케이지를 업데이트해도(1-1) 템플릿은 그대로 재사용된다

저장할 것: 조인트 이름 · 부모 · **월드 T/R/S** · `jointOrient` · `rotateAxis` · 부위 태그 · 툴 버전.

### 7-2. ~~자동 1차 배치~~ — **철회** (1-3)

1차 개정에서 제안했던 "이름/위치로 템플릿을 자동 배치" 는 **넣지 않는다.**
사용자가 손으로 하기로 확정했다. 자료 B 가 필요 없어진 것도 이 결정의 결과다(3장).

> 나중에 마음이 바뀌면 `A00145` 의 토큰 역색인 매칭(1000×1000 = 0.15s)을 노드 이름에
> 그대로 붙일 수 있다. **설계를 막지는 않는다** — `template_manager` 에 배치 함수를
> 하나 더 얹는 모양이 된다.

### 7-3. 좌우 **미러** — **세트 이름이 아니라 조인트 이름으로** 한다 ★

자료 I("매핑 표를 보고 미러 규칙을 만들라")에 대한 답이다. **표를 실제로 돌려 봤다.**

| 무엇을 미러 기준으로 | 결과 |
|---|---|
| **조인트 이름** (`_l` ↔ `_r` 접미사) | **31 / 31 성공 (100%)** |
| **세트 이름** (토큰 경계 `_L_`↔`_R_` · `_l_`↔`_r_` 치환) | 33개 중 **23 성공 / 10 실패** |

**실패하는 10개는 좌우에서 접두 번호까지 바뀐다.**

```
A01_Arm_L_01_UpperArm   <->  A02_Arm_R_01_UpperArm      (A01 -> A02)
B01_Leg_L_01            <->  B02_Leg_R_01               (B01 -> B02)
```

반면 어깨(`A03_Shoulder_L/R`) · 손가락(`CA01_Thumb_l/r_01`) · **다리 IK**(`B01_Leg_L/R_ik_*`)는
접두가 같아 치환만으로 맞는다. **즉 세트 이름에는 일관된 미러 규칙이 없다.**

→ **미러는 "왼쪽 템플릿 조인트의 트랜스폼을 오른쪽 템플릿 조인트로 옮기는 것"** 으로 정의한다.
세트 이름은 건드리지 않는다 — **오른쪽 세트는 이미 표에 적혀 있으므로 유도할 이유가 없다.**

> **부수 효과**: V01 `match_cage_arm_right` 가 임시 조인트를 **네 벌** 만들며 하던 미러
> (`R→L → 재orient → L→R`)가 통째로 사라진다.

기본은 **꺼짐**으로 두고 명시적으로 눌러야 동작하게 한다(1-3 의 "손으로 배치" 를 존중).

#### 옛 항목 (참고)

배치가 손 작업이어도, **왼쪽을 놓고 오른쪽은 버튼 하나**는 여전히 값어치가 있다.
다만 1-3 의 취지("손으로 하겠다")를 존중해 **기본 꺼짐 · 명시적으로 눌러야 동작**으로 둔다.
필요 없다고 하시면 빼면 된다 (자료 I 도 그때만 필요).

**부수 효과**: V01 `match_cage_arm_right` 는 `R→L 미러 → 재orient → L→R 미러` 로 임시 조인트를
**네 벌** 만든다. 템플릿 단계에서 좌우가 갈리면 **그 복잡도가 통째로 사라진다.**
→ 다만 결과가 V01 과 같은지 **수치로 비교**해야 한다(12장 Phase 4).

### 7-4. FK/IK 스위치 — **이번 작업의 최대 기술 리스크** ★★

1-5 로 `ikBlend` 가 스위치에 물려 있을 가능성이 크다. 그러면 `A00060` 의 IK Edit 이
이 경로를 탄다 (코드 실측 확인):

```python
plug = handle + ".ikBlend"
if _writable(plug):
    cmds.setAttr(plug, 0.0)              # 핸들 하나만 끈다  ← 안전
else:
    cmds.ikSystem(e=True, solve=False)   # 씬 전체 IK 정지  ← 위험
```

**씬 전역 폴백이 위험한 이유**

- 씬의 **다른 리그·다른 레퍼런스의 IK 까지** 멈춘다
- **씬이 아니라 세션 상태**다 — 마야를 다시 켜면 살아난다
  (`A00060` 은 편집을 되찾을 때 다시 꺼 주지만, 그건 그 툴을 열어야 동작한다)
- 편집 중 예외가 나면 **켜진 채로 남는다**

**대응 3단**

| 순위 | 방법 | 조건 |
|---|---|---|
| 1 | **스위치 어트리뷰트를 툴이 직접 0 으로 내렸다 복원** | 4-4 에서 스위치 이름을 알려주시면 |
| 2 | **전역 폴백을 쓰되 엄격한 트랜잭션** — `try/finally` 로 반드시 복원, 실패 시 `cancel_edit` | 항상 |
| 3 | Validate 가 **"이 핸들은 전역 폴백을 탄다"** 를 미리 경고 | 항상 |

**그리고 순서 규칙 하나**: **모든 핸들을 한 번에 열고 → 전부 옮기고 → 한 번에 닫는다.**
부위별로 열고 닫으면 IK 가 켜졌다 꺼졌다 하며 **다른 부위를 흔든다.**

### 7-5. IK 를 **미리 심고 편집만** 하는 것은 옳다 (유지) — **레퍼런스에서 확인됨**

> **2026-08-27 확인**: 케이지를 **레퍼런스로 불러와** 그 안의 조인트를 IK Edit 으로 고치는 것이
> 실제로 되는지 실측했다. **된다** — 다만 `A00060` 에 **조용한 버그가 하나 있어 고쳤다**(v03.02).
> `ikHandle -q -solver` 가 레퍼런스에서 `CAGE:ikRPsolver` 로 오는 바람에 솔버 이름 비교가
> 어긋나 **폴 벡터 갱신이 통째로 건너뛰어지고 있었다**(편차 위치 2.036 / 회전 45.77도,
> 경고 없음 → 지금은 **0.000000**).
>
> 함께 확인한 것 — 레퍼런스 노드에 `setAttr` · `addAttr` · `deleteAttr` 이 **전부 먹고**,
> 편집은 **reference edit 으로 저장되어 씬을 다시 열어도 남는다.** 편집 상태 어트리뷰트는
> 확정 시 지워지므로 **케이지 원본 파일은 안 더럽혀진다.** `rename` 만 막히는데 이 모듈은
> rename 을 쓰지 않는다. 자세한 건 `docs/A00060_jointTool_V03.md` §8.8.


근거가 실측으로 있다 — IK 를 끄고 체인만 고친 뒤 **핸들만 스냅하면 최대 편차 1.615**,
폴 벡터까지 역산해야 **0.00000000** 이다(`A00060` v01.05 개발 기록).
V01 처럼 매번 임시 IK 를 만들면 이름도 매번 달라지고 그 편차를 매번 새로 맞는다.

**자체 구현은 권장하지 않는다.** `ikBlend=0` 으로 내렸다 되돌리는 것만으로는 폴 벡터가
옛 평면을 가리켜 체인이 비틀린다. 검증된 코드가 있는데 다시 만들 이유가 없다.

### 7-6. **Validate 단계** — 넣는다 (사용자 승인)

빌드 전 점검. 전부 V01 이 "조용히 실패" 하던 항목이다.

| 점검 | 왜 |
|---|---|
| 템플릿 조인트가 부위별로 다 있는가 (개수·이름) | 빠지면 매칭이 밀린다 |
| **모든 템플릿의 `rotate` 가 0 인가** | orient 확정이 끝났는지 |
| 케이지의 `ikHandle` 이 다 있고 **폴 벡터 컨스트레인트가 붙어 있는가** | 4-1 · 타깃은 `targetList` 로 유도 |
| **`inspect()` 의 blockers** — 커브 솔버 · 이펙터 없음 · 폴 벡터가 컨스트레인트가 아님 | IK Edit 이 거부할 것을 미리 |
| **일직선 체인**이 있는가 | 폴 벡터 평면이 임의가 된다 |
| **`ikBlend` 가 구동되는가**(전역 폴백 경고) | 7-4 |
| 옵션 컨트롤러에 **`Arm_L` 등 어트리뷰트가 있는가** | 없으면 `setAttr` 이 `RuntimeError` (5-1 의 `Arm_r` 확인 포함) |
| 템플릿이 **skinCluster 에 들어가 있지 않은가** | 7-7 |
| 스케일이 1 인가 (템플릿·케이지) | 거리 수치가 틀어진다 |
| 레퍼런스 **네임스페이스가 예상과 같은가** | 8-6 |

### 7-7. 템플릿을 정말 **조인트**로 할 것인가 — 조인트로 하되 가른다

| 조인트의 위험 | 조인트여야 하는 이유 |
|---|---|
| `jointOrient` + `rotateAxis` **이중 회전**이 헷갈린다 | orient 를 그대로 컨트롤러에 물려줄 수 있다 |
| 아웃라이너에서 **아바타/케이지 조인트와 섞인다** | `A00060` 의 orient 기능을 그대로 재사용한다 |
| 실수로 **바인드에 들어간다** | 손으로 옮기기에 조인트 표시가 제일 편하다 |

→ **조인트로 하되**: 별도 최상위 그룹 + 고유 접두사(`TPL_`) · 표시색 통일 ·
Validate 에서 **skinCluster 편입 여부 점검**.

### 7-8. 부위 정의를 **데이터로 뺀다** ★ — **7-10 으로 대체됨(보류)**

> **2026-08-27**: 받은 매핑 표는 **부위(Arm Left …)가 아니라 조인트 단위**다. 그래서 Phase 1 은 아래의 부위 json 이 아니라
> **7-10 의 `template_map.json`** 을 쓴다. 부위 묶음(체크박스로 일부만 빌드)가 필요해지면

### 7-9. 매칭 모드(위치만 / 위치+회전) — **JSON 에 둔다 (해소됨)**

> **2026-08-27 해소**: 받은 매핑 표에는 **모드를 나타내는 이름 표식이 하나도 없다**
> (`_posOnly` 도, 다른 접미사도). 대신 사용자가 **글로** 지정했다 —
> *"B01_Leg_L_ik_01_foot, B01_Leg_R_ik_01_foot 세트는 위치만 매칭하고 회전값은 그대로 둬."*
> → 이름이 정보를 담고 있지 않으므로 **모드는 JSON 의 (조인트, 세트) 쌍에 적는 것 말고는 자리가 없다.**
> 아래 A안으로 확정한다. 7-10 의 스키마 참고.
>
> 지금 필요한 것은 **`B01_Leg_L_ik_01_foot` · `B01_Leg_R_ik_01_foot` 둘뿐**이고,
> 나머지 72개는 기본값(위치 + 회전)이다.

**옛 논의 (이름에 담지 않기로 한 근거 — 그대로 유효)**

**이름에 담지 않기로 한 근거** (사용자가 작성 중인 매핑 표에서 그대로 나온 것들)

- 이미 **`_pos` 로 끝나는 세트가 있다**(`C02_01_Neck_pos` · `C02_02_Head_pos`).
  파싱이 조금만 느슨하면 목·머리가 조용히 위치만 매칭된다.
- 표기가 흔들린다 — `A01_Arm_L_04_Pole`(대문자 P) vs `B01_Leg_L_06_pole`(소문자 p).
  이름을 규칙으로 삼으면 이런 흔들림이 전부 버그가 된다.
- **오타를 검증할 수 없다.** `_posOnly` 를 `_posonly` 로 치면 "다른 이름의 세트" 로 보일 뿐,
  에러 없이 전체 매칭으로 되돌아간다.
- 이름이 동작을 담으면 **이름을 바꾸는 순간 리그 동작이 바뀐다**
  (`A00330_NamingTool` 의 Set Rename 으로 일괄 치환이 가능해진 뒤로는 더 그렇다).

**남은 후보 두 가지** (이름 규칙 확정 후 결정)

| 안 | 내용 | 특징 |
|---|---|---|
| **A. 매핑 표에** | `{"set": "...", "match": ["t"]}` | 표는 **어차피 있어야 한다**(템플릿 조인트 이름은 케이지에 없는 툴 쪽 개념). 로드 시 검증됨 |
| **B. 세트 어트리뷰트** | `JUN_matchMode` | 리네임에 안 흔들리고 케이지가 자기를 설명한다. 다만 케이지에 세트를 더해도 **표를 고쳐야 하는 건 마찬가지** |

> **V01 은 이미 플래그로 풀고 있다.** `maya_scene.match_transforms(tgt, flw,
> match_rot_order, match_rot_axis, match_trs, match_rot)` 는 **플래그 4개**를 받고,
> `rig_matcher` 는 폴 오브젝트에 **`int_rot=0`**(위치만)을 넘긴다. 즉 켜고 끌 것은
> 2가지가 아니라 **4가지**이고, 이미 인자로 표현돼 있다.

### 7-10. 데이터 스키마 (Phase 1 에서 바로 쓴다)

`app/data/mapping/<version>/template_map.json` — 조인트 하나가 한 항목이다.

```jsonc
{
  "version": "1.0",
  "joints": [
    {
      "name":   "helper_foot_l",
      "parent": "helper_calf_l",          // 계층 (Phase 2 의 템플릿 생성이 이걸 쓴다)
      "targets": [
        { "set": "B01_Leg_L_03" },                            // 기본 = 위치+회전
        { "set": "B01_Leg_L_ik_01_foot", "match": ["t"] }     // 위치만 (7-9)
      ]
    },
    {
      "name":   "helper_ball_l",
      "parent": "helper_foot_l",
      "targets": [                        // ref 에서 줄이 둘로 나뉘어 있던 것을 합쳤다
        { "set": "B01_Leg_L_04" },
        { "set": "B01_Leg_L_ik_07_Ball" }
      ]
    },
    {
      "name":   "helper_root",
      "parent": null,
      "targets": []                       // 배치·계층용. 매칭 대상이 없다 (6-2)
    }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `name` | 템플릿 조인트 이름. **네임스페이스 없음** — 작업 씬에 로컬로 있다(7-11) |
| `parent` | 부모 조인트 이름. 루트는 `null` |
| `targets[].set` | 짝인 케이지 세트 이름. **네임스페이스 없이** 적고, 실행할 때 사용자가 고른 것을 붙인다 |
| `targets[].match` | `["t","r"]` 가 기본(생략 가능). `["t"]` 면 위치만 |

**나중에 짝이 늘거나 줄어도 이 파일만 고치면 된다**(1-8 요구). 케이지 버전이 갈리면
`<version>` 폴더를 늘린다(`A00090_ConnectionBuilder` 의 규칙 json 과 같은 방식).

### 7-11. 네임스페이스는 **케이지 쪽에만** 붙인다 ★

1-13 으로 사용자가 UI 에서 네임스페이스를 고른다. **어느 쪽에 붙일지가 중요하다.**

| | 어디에 사는가 | 이름 |
|---|---|---|
| **템플릿 조인트** | 작업 씬에 **로컬**(사용자가 놓는다) | `helper_foot_l` — 네임스페이스 없음 |
| **케이지 세트** | **레퍼런스**에서 온다 | `CAGE:B01_Leg_L_03` |

→ JSON 에는 **양쪽 다 네임스페이스 없이** 적고, 실행할 때 **세트 이름에만** 고른
네임스페이스를 붙인다. 콤보는 `cmds.namespaceInfo(listOnlyNamespaces=True, recurse=True)` 로
채우고 **"(none)" 항목**을 넣어 레퍼런스 없이 열린 씬에서도 되게 한다.

> 템플릿 조인트도 레퍼런스에서 오는 상황이 생기면 그때 필드를 하나 더 둔다.
> 지금은 그런 계획이 없다.

### 7-12. 그 밖에

- **모든 단계를 `undo_chunk` 로 1스텝** (V01 에는 없다 — 메모리 `undo-chunk-by-default`)
- **탭은 단계 순서로** — `Template / Orient / Validate / Controllers / Pose`.
  이 툴은 "카테고리" 보다 **"단계"** 가 자연스러운 상위 축이다
- **실패를 세어 보고** — V01 의 `except Exception: print(...)` 를 전부 없앤다

### 8-2. V01 `match()` 가 실제로 하는 일

1. Targets 로 **임시 조인트 체인**을 만든다 — 아바타 조인트를 직접 쓰지 않고 그 위치에 새로 만들어 orient 를 다시 잡는다
2. 부위별 orient — **spine** `orient_joint_none` · **arm** `xyz/yup` · **leg** `xzy/zup`(+ 끝 두 개 별도)
3. **오른팔은 미러를 4번** 탄다
4. helper 조인트에 **임시 IK** 를 걸고 폴 오브젝트를 `z±` 로 밀어 평면을 잡는다
5. Followers(세트면 멤버 전부)를 target 위치로 `xform` 매칭
6. **임시 조인트·임시 IK·임시 그룹을 전부 지운다**
7. 길이를 재서 옵션 컨트롤러 어트리뷰트에 쓴다 ← **늘어남/줄어듦의 실체**(1-4)

> **V02 에서 1·4·6 이 사라진다.** 템플릿이 1을 대신하고, IK 는 케이지에 상주하며 편집만 된다.

### 8-6. 이름 문자열 → **UUID** ★

이 워크플로는 **케이지와 아바타를 각각 레퍼런스로 불러온다.** 네임스페이스가 붙고,

(메모리 `uuid-safe-rename-duplicate-names` · `wip-tsl-uuid-selection` — 공용 TSL 이 이미
`(uuid, component)` 로 보관한다). **레퍼런스 워크플로에서는 선택이 아니라 필수에 가깝다.**

## 13. 열린 질문

0. **매핑 표에서 눈에 띈 것 — Phase 1 을 막지는 않지만 확인이 필요하다**
   - **`A00_Spine_0000` 만 4자리다.** 나머지는 `A00_Spine_01`~`05`.
     `A00_Spine_00` 오타인가, 실제 이름인가? → **틀리면 pelvis 매칭만 조용히 건너뛴다**(1-12).
   - **오른쪽 다리 IK 세트가 `B01_` 접두다** — `B01_Leg_R_ik_01_foot` … `B01_Leg_R_ik_07_Ball`.
     같은 오른쪽인데 비IK 는 `B02_Leg_R_01` 이다. 의도인가? → 매칭에는 지장이 없고
     **미러 규칙 도출에만 영향**을 준다(7-3 에서 이미 조인트 기준으로 우회했다).
   - **`helper_ball_l` / `helper_ball_r` 이 두 줄에 나온다**
     (`B01_Leg_L_04` 와 `B01_Leg_L_ik_07_Ball`). 한 조인트에 세트 둘 = 의도인가?
     → JSON 에서는 합쳐 둔다(6-2). **의도가 아니라면 한쪽을 빼야 한다.**
   - **폴 타깃**(`helper_polTgt_arm_l/r`, `helper_polTgt_leg_l/r`)은 `poleVectorConstraint` 가
     **위치만** 쓴다. V01 도 폴에 `int_rot=0` 을 넘겼다 — **`match: ["t"]` 로 두는 게 맞지 않나?**
     지금 표에는 모드 지정이 없어 기본값(위치+회전)으로 간다.
   - `CA05_Little_*` 로 **오타가 고쳐진 것**을 확인했다(예전 `CA05_Lttle_*`).
1. **부위를 늘릴 계획이 있나요?** (목 · 발가락 · 꼬리 · 날개 · 가슴)
   → 답변 3번을 **"늘어남(stretch)이 자동"** 으로 읽었는데, 제 질문은 **"부위 목록을 늘릴 계획"**
   이었습니다. 서로 다른 이야기라 다시 여쭙습니다.
   있으면 7-8(데이터화)의 우선순위가 올라갑니다. **없어도 7-8 은 그대로 할 값어치가 있습니다**
   (흩어진 상수를 모으는 것이므로).
2. **`D01_IK_handle` 안의 핸들 이름에 부위 토큰이 들어가나요?** (4-3 C 안)
   → 들어가면 부위별 부분 빌드가 공짜로 붙습니다. **Phase 4 에서만 필요합니다.**
3. **FK/IK 스위치 어트리뷰트 이름**은? (4-4) — 알면 씬 전역 폴백을 피할 수 있습니다.
   → **자료 D 에서 `helper_pvtgt` 이 빠진 자리에 이것만 남았습니다.**
4. **`Arm_r` 이 맞나요, `Arm_R` 오타인가요?** (5-1) — 오타라면 V01 에서 오른팔 길이가
   지금까지 안 써지고 있었다는 뜻입니다.
5. **템플릿 조인트의 목표 orient 규칙** — Phase 5 에서 필요합니다(자료 C 의 남은 절반).
   지금 코드에서 읽히는 것은 `arm: xyz/yup` · `leg: xzy/zup` · `spine: none` 인데,
   템플릿에도 그대로 가는지 확인이 필요합니다.
6. **템플릿 조인트를 매칭 후 지우나요, 남기나요?** — 남기면 다음에 다시 열어 고칠 수 있고,
   지우면 씬이 깨끗합니다. (저는 **남기고 숨기기**를 권합니다.)
