# A00220_BackupTool — Save Cache (빠른 저장 장치에 먼저 저장 → 원래 경로로 지연 복사) 구현 계획서

> **작성** 2026-11-04 · 상태: **계획 (구현 전, 0단계 진행 판단 필요)** · 대상 A00220 v01.21 → v01.22~, Maya 2023 ~ 2026
> 요청: 마야 파일을 HDD 에 저장할 때 매번 HDD 에 쓰지 말고 SSD(캐시 파일)에 먼저 저장 → 몇 초 뒤 캐시 파일을 원래 HDD 경로로
> 복사(같은 이름이면 덮어쓰기). n 개 파일을 작업해도 사람이 느끼는 저장은 SSD 속도, 원하는 HDD 경로에 저장되는 것은 보장.

## 0. 먼저 — 실측 결과와 진행 판단 (2026-11-04, 이 PC)

이 PC: **C: WD_BLACK SN850X (NVMe SSD)**, **D: Seagate ST4000DM004 (SATA HDD, 4TB)**.

### 0-1. 디스크에 그냥 쓰기 (python, 1MB 블록)

| 크기 | C: SSD | D: HDD | D: HDD + fsync(디스크까지 강제) |
|------|--------|--------|-------------------------------|
| 300 MB | 0.06 s | **0.07 s** | 2.08 s (144 MB/s) |
| 1500 MB | 0.33 s | **1.70 s** | 10.09 s (149 MB/s) |

→ **Windows 쓰기 캐시가 이미 "빠른 곳(RAM)에 먼저 쓰고 HDD 에는 나중에" 를 하고 있다.** 프로그램이 fsync 를 하지 않으면
수백 MB 는 HDD 도 SSD 와 같은 시간에 끝난다. 캐시(빈 RAM)를 넘는 GB 단위부터 HDD 가 느려진다.

### 0-2. 마야 실제 저장 (mayapy 2024, 폴리 3장 = 약 6M 버텍스, 히스토리 삭제)

| 형식 · 크기 | C: SSD | D: HDD |
|-------------|--------|--------|
| `.mb` 426 MB | 6.02 / 5.86 s | 5.91 / 4.22 s |
| `.ma` 904 MB | 4.06 / 4.13 s | 4.22 / 4.45 s |

→ **로컬 HDD 와 SSD 의 저장 시간이 같다.** 저장 시간의 거의 전부는 마야가 씬을 파일 형식으로 바꾸는 계산(CPU)이고,
마야는 fsync 를 하지 않아 디스크 쓰기는 OS 캐시가 흡수한다. **이 PC 의 로컬 HDD 에 대해서는 이 기능으로 빨라질 몫이 거의 없다.**

### 0-3. 효과가 날 수 있는 경우 (아직 측정 안 함 — 1단계에서)

| 경우 | 이유 |
|------|------|
| **네트워크 드라이브(NAS · SMB, 예: `\\172.30.1.93\MANUTeam\...`)** | SMB 쓰기는 OS 캐시가 로컬만큼 흡수하지 못하고 네트워크 대역폭(1GbE ≈ 110 MB/s)에 묶인다. 400 MB 면 4 초 안팎이 **마야 저장 시간에 더해질** 가능성이 크다. 팀원이 같은 NAS 를 쓰면 더 느려진다 |
| **빈 RAM 보다 큰 파일 / 연속 저장** | 0-1 의 1500 MB 처럼 쓰기 캐시가 넘치면 HDD 속도(약 150 MB/s, 이 드라이브는 SMR 이라 연속 쓰기에서 더 느려질 수 있다)가 드러난다 |
| 느린 외장 · USB HDD | 같은 이유 |

### 0-4. 진행 판단 (1단계 = 실측 게이트)

1단계에서 **사용자의 실제 작업 씬**으로 `C: SSD` · `D: HDD` · **NAS** 저장 시간을 잰다.
- NAS(또는 실제 목적지)에서 SSD 대비 **체감 차이(예: 1 초 이상 또는 30% 이상)** 가 나면 → 2단계부터 진행, 대상 기본값을 **네트워크 경로**로.
- 차이가 없으면 → 구현하지 않는다(복잡도 · 데이터 위험만 늘어난다). 이 문서는 근거로 남긴다.

## 1. 요구 정리

| # | 요구 | 설계 대응 |
|---|------|----------|
| R1 | 저장은 빠른 장치(SSD)에 먼저 | 마야의 저장 자체를 캐시 경로로 돌린다 (§3) |
| R2 | 몇 초 뒤 원래 경로로, 같은 이름이면 덮어쓰기 | 지연 복사기(flusher), 임시 이름으로 복사 후 **원자적 교체** (§5) |
| R3 | n 개 파일 동시 작업 | 목적지 경로마다 독립 큐, 같은 파일은 **최신 하나만** 복사(중간본 생략) (§4) |
| R4 | 원래 경로에 저장되는 것을 **보장** | 크기 · 해시 검증, 재시도, 실패 표시, 마야 종료 · 툴 재시작 · PC 재부팅 뒤 이어서 복사, 미반영 경고 (§6) |
| R5 | 사람이 느끼는 저장이 빠르다 | 마야는 캐시 저장이 끝나는 즉시 돌아온다. 복사는 마야 밖(A00220 프로세스)에서 |

## 3. 마야 저장을 캐시로 돌리기 (1 ~ 2단계에서 실측으로 확정)

| 후보 | 방법 | 확인할 것 |
|------|------|----------|
| **A (1순위)** | 저장 명령 바꿔 끼우기: `SaveScene` 런타임 명령 / Ctrl+S 핫키 / File > Save 메뉴를 훅 함수로 → `file -rename <cache>` → `file -save` → `file -rename <dest>` | rename 으로 되돌린 뒤 씬이 "수정됨" 으로 표시되는지, 타이틀 · Recent Files · `sceneName()` 이 dest 인지, `fileInfo`/`requires` 에 경로가 남지 않는지, 저장 콜백(kBeforeSave/kAfterSave)을 쓰는 다른 툴(A00220 Auto Backup 감지 포함)이 깨지지 않는지 |
| B | `MSceneMessage.addCheckFileCallback(kBeforeSaveCheck)` 에서 `MFileObject` 경로를 바꿔 저장 위치를 돌리기 | 저장에서도 경로 변경이 먹는지(열기 · 레퍼런스 체크와 달리 보장 안 됨) — 먹으면 A 보다 깨끗하다 |
| (제외) | 저장 뒤(kAfterSave) 복사 | 이미 HDD 에 다 쓴 뒤라 빨라지는 게 없다 |

범위:
- **대상만 돌린다**: 목적지가 규칙에 맞을 때만(§7 — 기본 네트워크 경로 · HDD). SSD 목적지는 그냥 저장.
- **Save As · Incremental Save · 마야 Autosave 는 v1 에서 손대지 않는다**(그대로 목적지에 저장) — 범위를 Save 한 경로로 좁혀 위험을 줄인다.
- 캐시 경로: `<cache_root>/<sha1(dest 정규화)[:12]>/<seq:06d>_<파일이름>` — 목적지마다 폴더, 저장마다 번호. 파일 이름은 그대로라
  씬 안의 상대 경로 문제가 없다(마야 상대 경로는 프로젝트 기준).

## 4. 큐 형식 (`job.json`, 저장마다 하나)

```json
{ "version": 1, "dest": "\\\\172.30.1.93\\MANUTeam\\...\\scene.mb", "cache": "C:/Users/.../save_cache/1a2b3c4d5e6f/000017_scene.mb",
  "seq": 17, "saved_at": "2026-11-04T15:02:11", "size": 446234112, "sha1": null,
  "dest_known": { "mtime": 1730700000.0, "size": 445998080 }, "host": "maya2024", "state": "pending" }
```

- 마야 훅은 **캐시 파일을 다 쓴 뒤** `job.json.tmp` → `os.replace` 로 job 을 올린다(반쯤 쓴 job 을 복사기가 보지 않게).
- **같은 dest 의 새 job 이 오면 옛 job 은 `superseded`** — 복사는 최신 seq 하나만(R3).
- `dest_known` = 마지막으로 이 시스템이 쓴 목적지의 mtime · 크기 → 다른 사람이 그 사이 목적지를 바꿨는지 판단(§5).

## 5. 지연 복사기 (A00220 `app/core/save_cache.py`, UI 비의존 · 표준 라이브러리)

1. job 을 받으면 **delay 초**(기본 5) 기다린다. 그 사이 같은 dest 에 새 job → 타이머 다시 시작, 옛 캐시는 지울 후보.
2. **충돌 확인**: 목적지의 현재 mtime · 크기가 `dest_known` 과 다르면(다른 사람 · 다른 PC 가 저장) **덮어쓰지 않고**
   `scene.conflict_<시각>.mb` 로 옆에 두고 빨간 경고. (사용자가 `Overwrite Anyway` 로 강행 가능)
3. 복사: `dest.~juncache` 로 1MB 청크 복사(진행률) → 크기 확인(옵션 sha1, 큰 파일은 꺼 둔다) → **`os.replace(tmp, dest)`**
   → 목적지가 반쯤 쓴 파일로 남는 순간이 없다(같은 볼륨 안 교체라 원자적). 원래 파일의 읽기 전용 · 잠김이면 실패 처리.
4. 성공: job `done`, 캐시 파일 삭제(옵션: 마지막 1 개 보관), `dest_known` 갱신, **기존 Auto Backup 에 "dest 저장됨" 알림**
   → 지금의 `scene_BU.mb` 백업 흐름이 그대로 이어진다(Save Delay 는 복사 완료 시점부터).
5. 실패: 지수 백오프 재시도(5 s → 10 s → … 최대 5 분), 상태 `failed` 표시, 캐시는 **절대 지우지 않는다**.
6. 동시성: 목적지마다 하나씩, 전체 동시 복사 2 개(HDD 탐색 경합 방지). 복사기는 QThread(UI 안 멈춤).

## 6. "원래 경로에 저장되는 것" 을 보장하는 장치

| 상황 | 대응 |
|------|------|
| 복사 전 마야 종료 | 마야 `quitApplication` 콜백: 미반영 job 이 있으면 "N file(s) still being copied" 창 — `Wait`(완료까지 진행 표시) / `Quit Anyway`(A00220 이 계속 복사). A00220 이 안 떠 있으면 Wait 만 |
| 마야 크래시 | 캐시 · job 이 SSD 에 남아 있다 → A00220 이 계속 / 다음 시작 때 이어서 복사 |
| A00220 종료 · PC 재부팅 | 시작할 때 큐 폴더 스캔 → `pending`/`failed` 재개. A00220 종료 시 미반영이 있으면 경고 |
| 복사 대기 중 같은 파일을 다시 열기 | 마야 열기 훅(kBeforeOpenCheck): dest 에 미반영 job 이 있으면 "newer copy in cache" → **캐시본 열기**(씬 이름은 dest 로) / 복사 끝날 때까지 기다리기 |
| 다른 씬이 이 파일을 레퍼런스 · 팀원이 NAS 에서 읽음 | delay + 복사 시간 동안은 **옛 버전**을 본다 — 문서 · UI 에 명시. 미반영 개수를 마야 상태줄(headsUp) · A00220 에 늘 표시 |
| 캐시 디스크 공간 | 상한(기본 20 GB) — 넘으면 새 저장은 캐시를 건너뛰고 목적지에 바로 저장 + 경고 |
| 캐시 폴더 자체가 깨짐 | 캐시 저장 실패 시 즉시 목적지에 일반 저장으로 폴백(저장이 사라지는 일은 없게) |

## 9. 시험 계획

- 코어: 저장 3 회 연속(delay 안) → 복사 1 회 · 최신 내용, 복사 중 프로세스 kill → 목적지는 옛 파일 그대로(반쪽 없음) · 재시작 후 완료,
  목적지 외부 변경 → 충돌 파일 + 원본 보존, 목적지 잠김 → 재시도 → 해제 후 성공, 디스크 가득 → 폴백.
- 마야: 훅 저장 뒤 `cmds.file(q=True, sn=True)` = dest, 수정 표시 없음, 캐시본 == 저장 내용, 열기 훅이 캐시본을 고름, 종료 경고.
- 성능: 저장 체감 시간(훅 전후) · 복사 시간 · 마야 프레임 영향(복사 중 마야가 느려지지 않는지 — 복사는 별도 프로세스).

## 10. 정할 것 (구현 전 사용자 확인)

1. **실제 목적지**가 로컬 HDD 인지 **NAS** 인지 — 0 장 실측상 로컬 HDD 는 이득이 거의 없다. 1단계에 쓸 실제 씬 · NAS 경로.
2. 마야 저장 돌리기를 **Ctrl+S / File > Save 에만** 걸어도 되는지(Save As · Autosave 제외).
3. 복사 대기 중 **다른 사람이 옛 파일을 볼 수 있는 것**(NAS 공유 시) 허용 여부와 delay 기본값(5 초).
4. 충돌(다른 사람이 그 사이 저장) 시 기본 동작 — 충돌 사본 남기기(권장) vs 덮어쓰기.
